# TravelAssist 外部订单纳入“我的旅行”设计

> 状态：v1.0 / 已确认设计  
> 日期：2026-09-05  
> 适用范围：Web“我的旅行”、行程总览、每日时间轴、地图、Reservation Hub、个人中心；未来手机 App 共用同一订单模型。

## 1. 设计目标

Booking.com、Agoda、Trip.com、Klook、GetYourGuide、Viator、OpenTable、TableCheck、航空公司、铁路、租车等外部订单，统一进入用户的“我的旅行”体系管理。

核心原则：

- 用户不需要区分“内部订单”和“外部订单”。
- 所有订单从用户视角都是当前旅行的一部分。
- Partner 来源作为订单属性显示，而不是单独建立一级导航。
- TravelAssist 负责统一展示、聚合状态、匹配行程、提醒和可执行操作。
- Partner 仍是最终订单、库存、支付、退款和履约的 Source of Truth。
- 不因会员状态限制酒店、门票、餐饮、交通等预订功能，以避免降低 Affiliate / Partner 返佣转化。

## 2. 不新增“外部订单”一级导航

不新增：

```text
外部订单
```

统一进入：

```text
我的旅行
  ↓
某次旅行
  ↓
总览 ｜ 地图 ｜ 日程 ｜ 预订 ｜ 预算 ｜ 设置
```

外部订单统一归入“预订”。

订单来源仅作为属性：

- Booking.com
- Agoda
- Trip.com
- Klook
- GetYourGuide
- Viator
- OpenTable
- TableCheck
- 航空公司 / 铁路 / 租车公司
- 确认邮件导入
- 手动添加

## 3. “我的旅行”主页新增预订完成度

旅行卡片由：

```text
日本关西 7日
9月12日 - 9月18日

[继续旅行]
```

调整为：

```text
日本关西 7日
9月12日 - 9月18日

预订完成度 72%

住宿    3/3
门票    5/7
餐饮    2/5
交通    1/3

⚠ 2项需要处理

[继续旅行]
```

旅行卡片可出现的摘要状态：

- ✓ 预订完整
- N 项待确认
- N 项订单冲突
- N 项同步失败
- N 项尚未预订
- 退款处理中

## 4. 单次旅行总览新增“预订摘要”与“需要处理”

### 4.1 预订摘要

```text
预订状态

住宿      ✓ 3/3
门票      5/7
餐饮      2/5
交通      1/3
租车      未安排

[查看全部预订]
```

### 4.2 需要处理

```text
需要您处理  3

⚠ 发现一笔新的 Booking.com 酒店订单
⚠ teamLab 门票与新干线时间冲突
○ Day 5 京都 → 东京 尚未购票

[查看全部]
```

“需要处理”不单独成为一级页面，作为旅行总览中的高优先级区域存在。

## 5. 导入已有预订

在旅行总览和 Reservation Hub 均提供：

```text
+ 导入已有预订
```

入口展开后按能力逐步开放：

```text
导入已有预订

○ 连接 Booking.com
○ 从确认邮件自动识别
○ 上传确认单 / PDF
○ 输入订单号
○ 手动添加
```

必须保留“手动添加”作为所有 Partner / API 不可用情况下的兜底。

## 6. 待匹配订单

外部订单被发现后，系统需要先尝试匹配 Trip / Day / Item。

示例：

```text
发现新的预订

Booking.com
THE GATE HOTEL 京都
9/12 - 9/14
2位成人

可能对应：
Day 3-4 · 京都住宿

[确认加入]
[查看详情]
[不是这个行程]
```

匹配状态：

- 自动匹配成功
- 建议匹配
- 等待用户确认
- 无法匹配
- 重复订单
- 已忽略

自动匹配应综合：

- 城市 / 地点
- 日期
- 住宿夜数
- 订单类型
- 行程中的空缺节点
- 用户 / 同行人数

## 11. 订单状态标准化

统一状态语言：

```text
已确认
等待确认
修改处理中
已修改
取消处理中
已取消
退款处理中
部分退款
已退款
订单失败
同步失败
```

示例：

```text
京都酒店

退款处理中
Booking.com

预计退款
¥38,500

最后同步
今天 14:35
```

TravelAssist 不得在 Partner 未确认前自行把订单显示为“已取消”或“已退款”。

---

## 12. “来源”与“可管理权限”分离

订单详情必须明确：

```text
来源
Booking.com

TravelAssist 可执行
查看 / 同步

需要前往 Booking.com
修改 / 取消
```

如果 Partner API 支持，则可显示：

```text
TravelAssist 可执行
查看 / 修改 / 取消
```

这样避免用户误认为 TravelAssist 对所有第三方订单都有直接操作权限。

## 13. 个人中心新增“预订与账户同步”

正式命名：

> **预订与账户同步**

不使用“绑定第三方账号”作为主文案。

示例：

```text
预订与账户同步

Booking.com
✓ 已连接
10分钟前同步

确认邮件
✓ 已连接
今天 13:20 扫描

Agoda
通过合作伙伴订单同步

[导入已有预订]
```

状态：

- 已连接
- 未连接
- 授权已过期
- 同步中
- 同步失败
- 重新授权
- 断开连接

账号连接属于可选增强功能，不作为通过 TravelAssist 发起预订的前置条件。

## 14. 重复订单检测

同一订单可能同时通过：

- Booking OAuth / Partner Sync
- Gmail / 确认邮件
- 手动添加

被多次识别。

必须设计去重：

```text
发现可能的重复订单

THE GATE HOTEL 京都
9/12 - 9/14

Booking.com 同步
确认邮件导入

[合并]
[保留两个]
```

系统匹配可参考：

- Partner Booking ID
- Confirmation Code
- 酒店 / 活动名称
- 日期
- 人数
- 金额

## 15. 订单冲突检测

不新增独立一级“冲突中心”，统一进入“需要处理”。

例如：

```text
需要处理 3

⚠ 京都酒店日期少1晚
⚠ teamLab门票与新干线冲突
⚠ 餐厅预约晚于最后一班地铁
```

冲突详情：

```text
原计划
teamLab 15:00-17:00

已购火车
16:15 东京站出发

建议：
方案A 调整teamLab到上午
方案B 更换17:30之后车次

[采用方案A]
[查看方案B]
```

高级自动冲突分析 / 自动重排可作为 Premium 月会员能力，但免费用户仍应看到基础冲突提示，并可自行修改行程。

## 16. “尚未预订”提示与商业转化

系统在识别已有订单后，可以准确知道行程中哪些项目尚未完成预订。

例如：

```text
尚未完成

○ Day 2 午餐
○ Day 4 京都 → 东京
○ Day 5 teamLab 门票
```

点击对应项目直接进入推荐 / 比价 / Partner 预订流程。

这一功能对所有用户免费开放，因为：

```text
更多有效预订
→ 更多 Partner 转化
→ 更多 Affiliate / Partner 返佣
```

不得把酒店、门票、餐饮、交通等核心预订入口设置为 Premium 专属。

## 19. 与会员体系的边界

已冻结原则：

### Free

- 酒店 / 景点 / 餐厅 / 交通搜索、比价、预订
- 通过 TravelAssist 发起的订单进入 Reservation Hub
- 查看自己的订单、Voucher、QR、取消规则
- 基础订单状态与冲突提示
- 手动导入 / 基础订单管理

### Premium 月会员

可提供增强能力：

- 外部确认邮件自动识别与整理
- 更高级的账号自动同步
- 自动冲突分析
- 异常发生后 AI 自动重排行程
- 高级主动提醒
- 价格持续监控
- 完整离线旅行包

原则：

> **会员收费不阻断任何能产生 Partner 预订和返佣的核心流程。**

## 20. 最终界面原则

用户视角：

> 所有订单都是“我的旅行的一部分”。

系统视角：

> 不同 Partner、不同同步方式、不同订单状态、不同操作权限。

UI 必须做到：

```text
统一展示
+
明确来源
+
明确状态
+
明确下一步操作
```

而不是把 Booking、Agoda、Klook 等各做一个独立入口。
