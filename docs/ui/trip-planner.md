# 行程主页面详细设计

> 状态：v0.1 / 核心布局已确定，细节持续完善

## 1. 页面定位

行程主页面是 TravelAssist 的核心工作区。

它同时承担：

- 地图查看
- 行程时间轴查看
- 推荐方案比较
- 旅行偏好设置
- AI 对话与调整
- 交通 / 住宿 / 餐饮 / 景点信息理解

目标不是把这些功能拆成许多页面，而是在一个沉浸式主界面中完成大部分旅行规划。

---

## 2. 桌面布局

推荐画面比例按宽屏 16:9 设计。

主结构约为：

```text
┌────────────────────────────────────────────────────────────┐
│                     地图主区域（约 75%）                    │
│                                                            │
│    路线 / 景点 / 住宿区 / 餐饮区 / 交通方式                │
│                                      ┌──────────────────┐  │
│                                      │ 详细设置         │  │
│                                      │                  │  │
│                                      ├──────────────────┤  │
│                                      │ 推荐 1           │  │
│                                      │ 推荐 2           │  │
│                                      │ 推荐 3 ...       │  │
│                                      └──────────────────┘  │
│                                                            │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ 时间轴：景点 → 交通 → 午餐 → 景点 → 晚餐 → 住宿     │  │
│  └──────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────┘
```

设计目标：

- 地图是背景和主内容，不要像普通后台左边地图右边表单那样割裂。
- 右侧设置栏使用“镶嵌 / 浮在地图上”的卡片感。
- 底部时间轴同样作为地图上的嵌入式信息层。
- 视觉上接近户外地图 / 行程工具，而不是传统 OTA 搜索结果页。

---

## 3. 地图层

地图需要能够表达整个行程，而不仅仅显示地点钉子。

### 3.1 每日路线

支持多日旅行，例如 3 天 2 晚：

- Day 1：起点 → 景点 → 餐饮 → 住宿
- Day 2：住宿 → 景点 → 活动 → 住宿
- Day 3：住宿 → 景点 → 终点

地图中需能区分不同日期的路线或当前选中日期。

### 3.2 景点标记

景点使用图钉 / 标记显示。

建议：

- 标记中可放象征性小图
- 选中后显示名称、时间、简要原因等
- 推荐但未加入行程的景点与已加入行程景点需要视觉区分

### 3.3 交通方式

路线段需表达交通方式，例如：

- 步行
- 电车 / 火车
- 公交车
- 其他公共交通

交通方式应同时显示在：

- 地图路线段
- 底部时间轴
- 必要时右侧方案摘要

### 3.4 推荐住宿区域

住宿初期可以优先推荐“区域”，而不是立即强迫用户选择具体酒店。

地图上可用半透明区域 / 柔和色块等方式表示：

- 推荐住宿区
- 适合当日行程的落脚范围

未来再在区域内推荐具体酒店。

### 3.5 餐饮区域

午餐 / 晚餐也可先推荐适合的区域，而不是把地图塞满餐厅图钉。

建议显示：

- 推荐午餐区域
- 推荐晚餐区域
- 用户展开后再显示具体餐厅候选

---

## 4. 底部行程时间轴

底部使用连续时间轴表达一天的真实节奏。

### 时间轴节点可以包括

- 时间
- 景点
- 活动
- 移动
- 交通方式
- 午餐
- 晚餐
- Check-in / 住宿

示例：

```text
09:00 清水寺
  ↓ 步行 15 分
10:30 二年坂 / 三年坂
  ↓ 公交 25 分
12:00 午餐区域
  ↓ 电车 20 分
14:00 伏见稻荷大社
  ↓
18:30 晚餐区域
  ↓
20:00 住宿区域
```

时间轴不仅是展示组件，也应逐步成为行程编辑入口。

未来可考虑：

- 拖动节点调整顺序
- 调整停留时长
- 删除节点
- 替换景点
- 修改交通方式

这些编辑方式尚未完全冻结。

## 5. 右侧详细设置

右侧上部只展示少量关键信息，并提供展开入口。

### 5.1 默认状态

默认可显示：

- 日期
- 人数 / 同行人概要
- 当前旅行节奏
- 交通关键偏好
- 景点喜好摘要
- `展开` / `详细设置`

不要在默认状态把所有小项目展开。

### 5.2 第一层展开：中项目

中项目是用户日常调整的主层级。

应支持快速设置。

例如：

- 同行人
- 日期 / 行程长度
- 移动偏好
- 景点与活动
- 餐饮
- 住宿
- 其他旅行条件

具体分类以偏好设计文档为准。

### 5.3 第二层展开：小项目

用户点击中项目后，再展开具体限制。

例如：

```text
移动偏好
├─ 少换乘
├─ 少步行
├─ 不乘坐公共交通
├─ 不乘坐公交
└─ 不乘坐游船
```

目标是让普通用户不必理解这些参数，但高级用户可以精确控制。

## 6. 同行人设置

同行人应放在较前位置。

当前讨论类型：

- 成人男性
- 成人女性
- 小孩
- 婴儿

系统可以根据组合辅助理解旅行属性，例如：

- 亲子
- 情侣
- 家庭
- 朋友

但这种推断只作为推荐层输入，不应覆盖用户明确设置。

同行人变化可能影响：

- 每日步行量
- 换乘容忍度
- 景点类型
- 休息频率
- 用餐时段
- 住宿区域
- 夜间活动安排

---

## 7. 推荐方案列表

右侧下部显示候选方案。

### 推荐 1

作为当前主推荐，显示较完整的简略行程，包括：

- 方案名称
- 核心特点
- 每日概要
- 主要交通特征
- 推荐原因

### 推荐 2 / 推荐 3 / 更多

默认只显示：

- 方案名称
- 一句差异说明
- 必要的关键指标

点击后切换为当前主方案，再展开详细信息。

这样可以避免右侧区域过于拥挤。

## 8. AI 在主页面中的位置

AI 不应与主页面割裂。

用户可以直接说：

- “第二天不要走这么多路。”
- “把伏见稻荷安排到早上。”
- “我们带婴儿，减少换乘。”
- “晚饭想吃当地料理。”
- “给我一个更轻松的版本。”

AI 需要：

1. 识别用户要修改的条件。
2. 转换成结构化设置。
3. 判断影响范围。
4. 重新计算受影响的行程。
5. 更新地图、时间轴、方案摘要。
6. 告诉用户发生了哪些变化。

---

## 9. 信息同步原则

同一旅行方案必须只有一个事实源。

不要分别维护：

- 地图版行程
- 时间轴版行程
- AI 文本版行程

而应由同一个结构化 Trip 数据生成所有视图。

```text
Trip State
 ├─ Map View
 ├─ Timeline View
 ├─ Recommendation Summary
 ├─ Settings Panel
 └─ AI Context
```

- 推荐住宿 / 餐饮区域的具体图形样式。

- 底部时间轴高度与展开方式。
- 时间轴是否支持第一阶段直接拖拽编辑。

- AI 对话在桌面版采用右下角浮层、侧边抽屉还是其他形态。
- 多方案最大显示数量。
