# TravelAssist 行程详细页 v2.0：Planner 无缝切换正式执行工作区

> 状态：v2.0 / 页面架构、Planner→Detail 无缝切换、地图/右栏/底部轨道与 AI 状态语义冻结  
> 更新日期：2026-09-05  
> Owner：A（旅行主系统）  
> 适用：TravelAssist Web 桌面端；Mobile 后续沿用相同 Trip / Day / Status 语义  
> 本版取代 v1.1 中“独立纵向执行页”作为桌面端主结构的方案；v1.1 中的执行数据、AI 双阶段判断、硬约束、预约状态等业务语义继续有效。

---

## 1. 最终产品定位

TravelAssist 不为“行程详细页”重新做一套视觉产品。

正式结构统一为：

```text
Trip Workspace
├─ Planner Mode    规划模式
└─ Detail Mode     正式行程详情 / 执行模式
```

用户从 Planner 进入正式行程详情时：

- 顶部主导航不变；
- 地图不消失、不重新载入成另一种产品；
- 左侧地图工具栏继续复用；
- 右侧栏原位换成“当日执行仪表盘”；
- 底部栏原位换成“日期快速选择 + 单日横向行程轨道”；
- 地图路线从“多日规划比较”过渡为“当前日彩色 + 前后日灰色上下文”。

核心体验：

> **不是离开 Planner 去另一个页面，而是同一个旅行工作区从“怎么计划”进入“正式怎么走”。**

工程上必须把两种 View 分开，不允许靠一个巨型组件不断堆叠 `if planner / if detail`。

---

## 2. Planner 与 Detail 的职责边界

| 模式 | 用户要回答的问题 | 核心 UI |
|---|---|---|
| Planner | “这趟旅行怎么安排？” | 地图、多日路线、偏好、推荐方案、重算 |
| Detail | “这一天具体怎么执行？” | 当前日地图、日程轨道、AI 状态、当日数据 |
| T-48h 后 PRO Execution | “现实已经变化，后面怎么办？” | 实时判断、后续影响、调整建议 |

Detail Mode 不允许重新出现：

- 推荐方案 1 / 2 / 3；
- 更多行程偏好设置；
- `1日 / 3日 / 全日` 规划尺度按钮；
- “重新生成整个路线”；
- 大量推荐景点内容流。

Detail Mode 使用：

- `调整后续行程`；
- `AI 重新检查`；
- 单节点编辑；
- 新增节点；
- 当前日/预约/现实状态判断。

## 3. 共用 Trip Workspace 外壳

以下界面元素 Planner 与 Detail 完全继承：

```text
Top Navigation
├─ TravelAssist Brand
├─ 探索目的地
├─ AI 行程规划
├─ 旅行灵感
├─ 实用工具
├─ 搜索
├─ 通知
└─ 用户头像

Main Workspace
├─ Map
├─ Map Layer Toolbar
├─ Right Sidebar Slot
└─ Bottom Panel Slot
```

视觉继续采用当前已确定的 TravelAssist 风格：

- 暖白 / 象牙白底；
- 淡樱花粉、浅暖橙作辅助；
- 深海军蓝文字；
- 低饱和地图与自然色；
- 大圆角但不过度卡通；
- 轻边框、轻阴影、浅半透明面；
- 樱花 / 日式水彩元素只做环境装饰，不干扰数据阅读；
- 地图仍然是屏幕视觉主体。

## 4. Planner → Detail 无缝切换

### 4.1 进入条件

当用户已经选择/采用一个正式方案后，在 Planner 提供明确入口：

```text
[查看正式行程]
```

或：

```text
[进入行程详情]
```

入口必须继承：

- 当前 selected plan；
- 当前 Trip State；
- 当前 Day；
- 当前地图视野（可在必要时轻微 fit bounds）；
- 已有预约/酒店/餐饮等数据。

不得重新创建第二套 Trip Mock。

### 4.2 动画与视觉过渡

建议 180–260ms 的轻量过渡：

```text
Planner 推荐方案 / 偏好设置
        ↓ fade / slide
Detail 当日仪表盘

Planner 底部多日预览
        ↓ fade / layout transition
Detail 日期按钮 + 当日轨道

Planner 多日彩色路线
        ↓ route style transition
当前日彩色 + 邻近日灰线
```

地图本体不要闪白、不要重新 Mount。

支持 `prefers-reduced-motion`：关闭非必要过渡。

## 5. Detail Mode 地图规则

### 5.1 删除规划范围控件

Detail Mode 删除地图上的：

```text
1日
3日
全日
```

日期切换统一由底部栏顶部的 Day Quick Selector 完成。

### 5.2 路线层级

选中 Day N 时：

```text
Day N
= 当前正式路线
= 保留原方案颜色 / 主色
= POI / 当前节点正常展示

Day N-1
= 只保留路线
= 中性浅灰
= 不显示大面积照片 Pin / 推荐区域

Day N+1
= 只保留路线
= 中性浅灰
= 不显示大面积照片 Pin / 推荐区域

其他日期
= 默认隐藏
```

原则：

> 当前日回答“今天怎么走”；前后日只回答“这一天接在什么上下文里”。

### 5.3 地图与底部轨道联动

- 切换日期 → 地图同步切换当前日彩色路线；
- 点击时间轴气泡 → 地图选中对应地点 / 路段；
- 点击地图当天正式 POI → 底部轨道定位对应节点；
- Modal 打开时地图保持背景，不替换主工作区；
- 未来 Current Location 接入后，当前位置属于 Detail Mode 的地图数据层。

## 6. Detail Mode 右侧栏：当日执行仪表盘

右栏约占页面宽度 1/4，整体保持与 Planner 一样的镶嵌式卡片语言。

信息顺序必须固定：

```text
AI 行程分析
↓
当日概况
↓
预计开销
↓
活动时间
↓
酒店信息
↓
餐饮信息
↓
预约 / 门票
↓
交通 / 停车 / 提醒
```

不需要每个区块都有照片。酒店/餐饮可在空间允许时使用小型缩略图，时间轴气泡禁止照片。

## 7. AI 行程分析：右栏第一优先级

顶部显示四个计数：

```text
✅ 正常       5
⚠ 需注意     1
❗ 有问题     0
❓ 待确认     1
```

### 7.1 状态必须拆成两个维度

#### AI 判断状态

| 状态 | UI | 含义 |
|---|---|---|
| normal | 无告警 / 绿色正常 | 当前无需用户介入 |
| warning | 黄色 `!` | 有风险、AI 建议确认、需要用户选择 |
| error | 红色 `!` | 已确认或高置信度存在问题 |

#### 预约状态

| 状态 | UI | 含义 |
|---|---|---|
| confirmed | 绿色 `✓` | 订单 / 预约已确认 |
| unknown | `?` | 状态未知 / 等待确认 |

同一节点可同时存在：

```text
15:00 美术馆
✓ 门票已确认
❗ 预计无法按预约时间到达
```

预约已确认不能覆盖现实执行风险。

## 8. AI 双阶段判断

### 8.1 Planning Review：出发前 T-48h 之前

核心问题：

> **这份行程设计本身是否合理，并符合用户需求？**

扫描整个旅行，主要检查：

- 用户需求匹配；
- 每日强度是否过高 / 过低；
- 时间与停留长度；
- 地理顺序 / 明显绕路；
- 驾驶强度；
- 交通衔接；
- 营业日 / 休馆日；
- 季节适配；
- 日出 / 日落条件；
- 同行人适配；
- 酒店位置；
- 餐饮时段；
- 已确认预约冲突；
- 应预约但尚未预约；
- 备用方案完整性。

遥远未来天气不能因为预测不稳定直接标红。

### 8.2 Execution Monitor：从 T-48h 到行程结束

核心问题：

> **根据现实最新状态，这一天现在还能不能顺利执行？**

综合：

- 小时级天气；
- 航班 / 铁路 / 公交；
- 道路封闭 / 事故 / 拥堵；
- 景点临时闭馆；
- 缆车 / 游船 / 户外设施运行；
- 用户当前位置；
- 实际出发 / 到达；
- 当前延误；
- 实际停留；
- 后续硬预约；
- 当前订单状态；
- 停车 / P+R（数据可得时）；
- 日落 / 光线条件；
- 用户临时修改；
- 后续连锁影响。

监控范围默认：

```text
当前节点
+ 今天剩余节点
+ 最近硬约束
+ 未来 24–48h 高风险 / 硬约束
```

使用“事件触发 + 局部重算”，不允许每分钟全量分析整趟旅行。

```text

天气

预计结束时间
总活动时长
```

```text

步行            6.8km

硬预约          2项
自由/缓冲       1.5h
```

```text
其他
────────
当日预计
```


## 11. 酒店信息

至少展示：

- 酒店名称；
- 入住时间；
- 最晚入住（若有）；
- 次日退房时间；
- 地址；
- 停车；
- 早餐；
- Reservation 状态；
- 订单入口；
- 导航入口。

换酒店日必须能同时理解：

```text
早晨：Hotel A 退房
晚上：Hotel B 入住
```

酒店入住/退房本身也属于正式 Timeline Item。

## 12. 餐饮信息

当天汇总：

- 早餐；
- 午餐；
- 晚餐；
- 推荐用餐时间；
- 已固定餐厅 / 仅餐饮区域；
- 预约状态；
- 预算；
- 是否允许顺延。

## 13. 预约 / 门票

右栏显示今天的预约摘要：

```text
✓ 10:30 美术馆

✓ 17:30 演出
```

订单来源（TravelAssist / Booking.com / Klook / 邮件导入等）只是属性，不改变用户操作。

## 14. 交通 / 停车 / 提醒

尤其为自驾和复杂公共交通保留：

- 当日主要驾驶里程；
- 驾驶时间；
- 高速 / 收费；
- P+R；
- 停车目标；
- 换乘；
- 加油 / 充电；
- 冬季装备 / 限行（需要时）；
- 关键“最晚出发”时间；
- 未来硬预约对当前段的约束。

交通是正式一等数据，不是景点之间的一句小字。

## 16. Day Quick Selector 放在底部栏顶部

该选择器替代原底栏标题“第2天 · 4月11日”的位置。

示例：

```text
‹
第1天           第2天（当前）              第3天
4/10 东京       4/11 河口湖·富士山·箱根   4/12 箱根·东京
```

规则：

- 当前日突出；
- 点击后地图、右栏、时间轴同步；
- 选择器是 Detail Mode 唯一的主要日期切换入口；
- 不再在地图放 `1日 / 3日 / 全日`。

## 17. 单日横向行程轨道

时间轴按真实时间比例或经过可读性约束后的准比例排列：

```text
08:30      10:00       12:30       14:00       17:00      19:00
  ●─────────●───────────●───────────●───────────●──────────●
```

所有状态放在“轨道节点”上。

### 17.1 节点状态

```text
绿色圆点     正常 / 已完成 / 已确认执行状态
黄色圆点     AI 需要确认
红色圆点     已存在明确问题
灰色圆点     待确认 / 未开始 / 未知（按具体状态文案辅助）
```

不能只依赖颜色；Hover / Focus / Tooltip 或辅助文本必须给出语义。

## 18. 气泡：上下交错、无照片、弱透明分类色

轨道节点上下交错连接小型长方形气泡：

```text
      ┌ 酒店出发 ┐          ┌ 午餐 ┐          ┌ 前往箱根 ┐
      │ 08:30    │          │12:30 │          │17:00    │
      │ 巴士1.5h │          │ 1h   │          │ 电车1h  │
      └──────────┘          └──────┘          └─────────┘
            │                    │                  │
─────────── ● ─────── ● ─────── ● ────── ● ────── ● ──────
                      │                  │
                 ┌ 河口湖 ┐        ┌ 富士急乐园 ┐
                 │10:00   │        │14:00      │
                 │游览1.5h│        │游玩3h     │
                 └────────┘        └───────────┘
```

### 18.1 气泡禁止内容

- 不放照片；
- 不再放绿色勾；
- 不重复黄色 / 红色状态标签；
- 不放长篇地点介绍；
- 不塞完整 AI 解释。

### 18.2 气泡只显示

- 时间；
- 标题；
- 类型 / 简短行为；
- 停留时长或移动时长；
- 必要时一行最关键副信息。

### 18.3 分类颜色

| Item 类型 | 背景建议 |
|---|---|
| Attraction | 淡青 / 淡绿 |
| Dining | 淡暖橙 |
| Transit / Drive | 淡蓝 |
| Hotel | 淡粉 / 淡紫 |
| Activity | 淡紫 |
| Task / Buffer | 淡灰蓝 |

全部使用低饱和、低透明度背景。

冻结原则：

> **气泡颜色回答“这是什么”；轨道圆点颜色回答“它现在怎么样”。**

## 20. 点击气泡：项目详情 Modal

点击任意气泡后：

- 居中打开 Modal；
- 背景轻微 Dim；
- 右侧“当日仪表盘”不被替换；
- 地图保持在背景；
- 点击 Modal 外部关闭；
- `Esc` 关闭；
- 关闭后焦点返回原气泡。

Modal 建议分区：

```text
项目标题 / 状态

详情
├─ 时间
├─ 地点
├─ 时长
├─ 类型
├─ 交通
├─ 预约 / 门票

├─ 证据 / 更新时间

[更改内容]
```

## 22. 编辑、保存与 AI 检查

最终采用混合模式。

### 22.1 自动草稿保存

用户编辑后：

```text
保存中…
→ 已自动保存
```

实现阶段可采用 2–3 秒 idle debounce。

### 22.2 自动轻量检查

每次有意义的编辑后，本地/低成本检查：

- 时间是否合法；
- 是否与上下项目重叠；
- 必填字段；
- 明显不够的移动时间；
- 是否撞到临近硬预约；
- 基础日程边界。

### 22.3 完整 AI 判断手动触发

不要每输入一个字就全量调用 AI。

提供：

```text
[AI 重新检查]
```

用于：

- 完成一轮编辑；
- 重新评估整天；
- T-48h 后重新评估当前及后续窗口。

## 23. AI 修改必须 Preview → Apply

AI 不允许静默修改正式 Timeline。

示例：

```text
当前延误 +35min

原计划
16:00 湖边 75min
17:45 小镇 60min
19:30 晚餐（已预约）

建议
16:15 湖边 45min
17:30 小镇 30min
19:30 晚餐（保持）

[保持原计划]
[采用调整]
```

执行顺序：

1. 保留硬约束；
2. 保留必须项目；
3. 压缩缓冲；
4. 压缩允许缩短的时长；
5. 删除可删项目；
6. 启用备用项目；
7. 最后才建议更改重要预约。

Detail Mode 统一用：

```text
调整后续行程
```

而不是 Planner 的：

```text
重新生成路线
```

## 25. 路由策略

### 当前 Web MVP 阶段

在正式 Trip ID / DB Contract 尚未完成前，优先使用可迁移的工作区 View 契约，例如：

```text
/planner?view=detail&day=2
```

优势：

- 真正复用现有 Planner Workspace；
- 切换无感；
- 不伪造持久化 Trip ID；
- Back / Forward / Refresh 可恢复当前 Detail Day。

### 最终 Trip Contract 成熟后

迁移目标：

```text
/trips/{tripId}/plan
/trips/{tripId}/detail?day=2
```

组件层不得依赖临时 URL 结构，避免二次重写。

## 29. 最终冻结原则

1. **详情页继承 Planner 的同一个地图工作区，不再创造第二套视觉框架。**
2. **工程上 PlannerView 与 DetailView 分开，共用 Trip Workspace。**
3. **地图：当前日彩色，前后日只保留灰线，其余隐藏。**
4. **地图上的 `1日/3日/全日` 在 Detail Mode 删除。**
5. **右栏：AI 状态 + 当日执行数据，而不是偏好 / 推荐方案。**
6. **底栏顶部：整趟旅行 Day 快速选择。**
7. **底栏主体：单日横向轨道，状态只显示在轨道圆点。**
8. **气泡：无照片、半透明分类色、上下交错、只保留简易执行信息。**
9. **点击气泡：居中 Modal；点击外部关闭；右栏保持当天总览。**
10. **编辑后自动草稿保存 + 轻量检查；完整 AI 检查由明确动作触发。**
11. **行程前 AI 审计划；T-48h 后 AI 盯执行。**
12. **AI 修改必须先预览，用户确认后才应用正式后续行程。**

最终体验目标：

> **Planner 把计划做出来；同一张地图顺滑进入 Detail，把计划真正走完。**
