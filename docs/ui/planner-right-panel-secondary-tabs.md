# TravelAssist Planner 右栏子菜单与底部辅助 Tab 重设计

> 状态：v0.4 / 推荐冻结方案 / 待并入 Planner 主设计书  
> 更新日期：2026-09-06  
> Owner：A / Main Travel System  
> 适用页面：`/planner`  
> 关联文档：`docs/ui/trip-planner.md`、`docs/ui/planner-map-interaction-booking-mapbox.md`  
> 影响范围：右栏上半设置区，以及底部除“行程”外的 5 个 Tab  
> 不改变：地图约 75% / 右栏约 25%、右栏上下约 1:1、底部栏默认约页面高度 25%、三方案横条、地图日程范围选择器

---

# 1. 本轮重新设计的结论

当前 Planner 的功能项目已经足够完整，主要问题不是“缺少设置”，而是：

1. 右栏默认态容易像一组压缩后的表单卡，摘要、入口与重要程度没有明显主次；
2. 三级偏好内容很多，但若全部继续用普通 Popover 堆叠，会显得拥挤且难以定位；
3. 底部 5 个辅助 Tab 目前以“应显示哪些字段”为主，尚未形成各自明确的视觉叙事；
4. `详细` 容易成为所有剩余信息的收纳箱，用户无法立即理解它的价值；
5. 五个 Tab 若分别采用不同布局，会破坏整个底栏的一体感。

本轮推荐方案：

> **右栏采用“摘要工作台 + 上下文子菜单”；底部采用“固定骨架 + 不同信息画布”。**

右栏只负责回答：

- 当前和谁去、哪天去；
- 玩、吃、住的核心偏好是什么；
- 是否存在尚未用于重新规划的修改。

子菜单负责回答：

- 具体怎么改；
- 这些修改会影响哪些日期、节点与预约；
- 是仅保存偏好，还是据此重新规划。

底部 5 个辅助 Tab 分别回答：

| Tab | 核心问题 |
|---|---|
| 交通 | 今天 / 这几天具体怎么移动，哪里麻烦 |
| 预约 | 哪些已经完成，哪些必须马上处理 |
| 天气 | 天气会影响哪里，有什么可直接替换的备选 |
| 吃住 | 每天在哪里吃、住在哪里，是否顺路且已确认 |
| 体检 | 这份行程是否合理，哪里需要优化 |

# 2. 名称与兼容策略

底部内部数据 ID 保持不变，避免影响已有状态与后端模型；只调整界面显示名称。

| 现有显示名 | 推荐显示名 | 内部 ID | 说明 |
|---|---|---|---|
| 行程 | 行程 | `itinerary` | 保持不变 |
| 移动 | 交通 | `mobility` | “交通”更像用户语言 |
| 预约·票务 | 预约 | `booking` | 票务仍属于预约内容 |
| 天气·备选 | 天气 | `weather` | 备选是天气 Tab 内的核心动作，不必写进标题 |
| 住宿·餐饮 | 吃住 | `stayDining` | 更短，适合窄 Tab 栏 |
| 详细 | 体检 | `details` | 从“杂项详情”改为“行程质量检查” |

宽屏可显示完整辅助说明：

```text
交通
预约
天气
吃住
体检
```

窄屏仍使用相同短名，不再依靠截断文字。

# 3. 右栏上半默认态

## 3.1 设计目标

右栏默认态不直接展示大量控件，只展示：

- 当前条件摘要；
- 五个高频入口；
- 修改状态；
- 重新规划动作。

默认态应像“当前方案的控制台”，而不是“缩小版设置页面”。

## 3.2 推荐结构

```text
┌────────────────────────────────┐
│ 行程设置              已应用   │  36px
├────────────────────────────────┤
│ 东京 · 3天2晚                  │
│ 4/10—4/12     2成人 · 1儿童    │  64px
├────────────────────────────────┤
│ ◉ 想怎么玩                     │
│   自然风光 · 摄影 · 经典地标  ›│  52px
├────────────────────────────────┤
│ ◌ 想吃什么                     │
│   当地料理 · 日料 · 甜品      ›│  52px
├────────────────────────────────┤
│ ◇ 想住哪里                     │
│   靠近车站 · 安静 · 连住优先  ›│  52px
├────────────────────────────────┤
│ ☷ 更多条件                     │
│   适中节奏 · 少步行 · 中等预算›│  52px
├────────────────────────────────┤
│ [更多行程设置] [重新规划路线]  │  44px
└────────────────────────────────┘
```

其中第一张 64px 摘要卡分成两个可点击热区：

- 左侧 / 上侧：旅行日期；
- 右侧 / 下侧：同行人。

不再为“同行人”和“旅行日期”分别占用两张完整卡片。

## 3.3 信息层级

### 第一层：标题与状态

左侧：

```text
行程设置
```

右侧状态只允许三类：

- `已应用`；
- `有 3 项未规划`；
- `规划中…`。

状态不能只靠圆点颜色，应同时显示文字。

### 第二层：基础条件摘要

显示：

- 主要目的地 / 行程名称；
- 日期区间；
- 天数与晚数；
- 同行人数摘要。

这里不显示天气、费用、预约数，避免和底部 / 方案区重复。

### 第三层：玩、吃、住、更多条件

使用统一“设置行”：

```text
小图标 + 标题
当前摘要（最多 2 行）
右箭头
可选状态徽标
```

摘要最多 3 个关键词，超出后显示 `+N`：

```text
自然风光 · 摄影 · 经典地标 +2
```

### 第四层：操作区

左：`更多行程设置`  
右：`重新规划路线`

两者同高、同圆角；右侧按钮视觉更明确，但不使用过强大面积纯色。

当有未用于规划的修改时，右侧按钮自动变为：

```text
预览 3 项变更
```

预览后再显示：

```text
应用新路线
```

# 4. 子菜单统一外壳

## 4.1 形态

除简单人数 / 日期面板外，所有偏好子菜单使用同一种“锚定式设置层”。

推荐尺寸：

- 宽：`440–480px`；
- 最大高：`min(640px, viewport - 96px)`；
- 从右栏向左覆盖地图；
- 不改变地图、底栏、右栏方案区尺寸；
- 与触发项保持 8–12px 视觉连接。

```text
地图区域                 右栏
          ┌──────────────┐┌────────┐
          │ 上下文设置层 ││触发行  │
          │              ││        │
          └──────────────┘└────────┘
```

## 4.2 固定组成

```text
┌────────────────────────────────────┐
│ 标题       当前摘要        重置  × │ 56px
├────────────────────────────────────┤
│ 影响提示：将影响第 2–3 天           │ 32px，可选
├────────────────────────────────────┤
│                                    │
│ 可滚动设置内容                      │
│                                    │
├────────────────────────────────────┤
│ 已修改 3 项   [取消] [保存设置]     │ 64px
└────────────────────────────────────┘
```

底部操作保持吸附，不随内容滚走。

## 4.3 三级结构

统一为：

```text
Level 1：右栏摘要
Level 2：子菜单内的快速设置
Level 3：当前子菜单内联展开的详细设置
```

禁止继续打开第三个浮层。Level 3 应在当前面板内用折叠区、分段控件或抽屉式内容展开。

## 4.4 控件规范

优先使用：

- Chips：类别与倾向；
- Segmented Control：互斥选择；
- Slider：预算、节奏、步行、排队；
- Time Range：出发、返回、用餐窗口；
- Stepper：人数、房间数；
- Switch：是否允许、是否自动处理；
- Search Token：必去 / 不去 / 已锁定地点。

避免：

- 一屏连续十几个开关；
- 只有标题没有当前摘要的设置项；
- 需要用户记忆含义的图标按钮；
- 长表单式下拉菜单；
- 多层 Modal 套 Modal。

## 4.5 变更状态

用户修改设置后：

1. 当前控件立即更新；
2. 子菜单底部显示 `已修改 N 项`；
3. 点击 `保存设置` 后回到右栏；
4. 右栏状态变为 `有 N 项未规划`；
5. 原 `重新规划路线` 变为 `预览 N 项变更`；
6. 用户确认影响范围后才应用新路线。

偏好修改不应每次点击都触发昂贵的路线重算。

# 5. 同行人子菜单

## 5.1 默认视觉

使用 2×2 人数卡，不使用四行普通 Select。

```text
┌──────────────┬──────────────┐
│ 成人男性  1  │ 成人女性  1  │
│      −  1  + │      −  1  + │
├──────────────┼──────────────┤
│ 儿童      1  │ 婴儿      0  │
│      −  1  + │      −  0  + │
└──────────────┴──────────────┘
```

当儿童 / 婴儿大于 0 时，下面展开年龄 Chips：

```text
儿童年龄   [5岁] [8岁] [+ 添加]
婴儿年龄   [1岁] [+ 添加]
```

## 5.2 同行特征

快速 Chips：

- 老人同行；
- 婴儿车；
- 行动较慢；
- 需要无障碍；
- 需要儿童座椅；
- 分房住宿。

这些是同行特征，不新增人员种类。

## 5.3 影响摘要

面板底部显示轻量推算：

```text
预计需要 2 间客房
儿童票 / 家庭设施将纳入筛选
步行与换乘强度将自动降低
```

# 6. 旅行日期子菜单

## 6.1 首屏

顶部直接显示：

```text
4月10日 周六  →  4月12日 周一
3天2晚
```

下方使用日期区间日历；不使用两个彼此独立、容易填反的日期框。

## 6.2 行程可用时间

日期下方增加首尾日真实可用时间：

```text
首日可开始       13:30
末日需结束       16:00
```

这比只记录日期更能防止首日 / 末日被排满。

## 6.3 可调整性

可选项：

- 日期固定；
- 可前后调整 1 天；
- 仅首日可调整；
- 仅末日可调整。

## 6.4 修改影响

若已有预约，先显示影响，不直接覆盖：

```text
受影响：第 3 天酒店、1 项门票
不受影响：2 项锁定预约
```

确认后才保存。

# 7. 景点偏好子菜单

## 7.1 顶部摘要

显示当前旅行重点，并允许拖动排序：

```text
1 摄影
2 自然风光
3 历史文化
```

最多常驻显示 5 项，更多项仍可选择，但不进入最高优先级。

## 7.2 快速设置分组

### 看什么

- 自然风光；
- 历史文化；
- 城市探索；
- 经典地标；
- 博物馆 / 展览；
- 展望台 / 夜景。

### 做什么

- 当地体验；
- 温泉；
- 徒步；
- 购物；
- 主题乐园；
- 水族馆；
- 亲子活动。

### 怎么玩

- 摄影优先；
- 本地感；
- 少排队；
- 雨天友好；
- 室内优先；
- 自由探索。

## 7.3 偏好强度

选中 Chip 后，可在右侧选择：

```text
喜欢 / 优先 / 核心
```

不使用“重复点击 Chip 在三个状态之间循环”的隐藏交互。

## 7.4 Level 3 详细设置

折叠分组：

1. `必去与不去`：地点搜索 Token；
2. `人群与排队`：最大排队时间、热门高峰容忍；
3. `摄影时段`：日出、Golden Hour、日落、夜景；
4. `停留方式`：单点最长停留、自由探索比例；
5. `体力要求`：徒步强度、连续户外时长；
6. `预约活动`：是否优先安排可预约项目。

# 8. 餐饮偏好子菜单

## 8.1 安全信息置顶

过敏与不可接受项必须放在最上方，不能藏在“更多设置”最深处。

```text
饮食限制
[花生过敏] [不吃猪肉] [+ 添加]
```

使用淡警示边框，不使用大面积红色。

## 8.2 两个视图

```text
[总体偏好] [按餐次]
```

### 总体偏好

- 当地料理；
- 日料；
- 海鲜；
- 拉面；
- 烧肉 / 和牛；
- 居酒屋；
- 咖啡；
- 甜品；
- 小吃；
- 高级餐厅；
- 快速简餐；
- 夜宵。

### 按餐次

分别设置：

- 早餐；
- 午餐；
- 晚餐；
- 夜宵。

每餐只显示时间、预算、形式、是否需要预约。

## 8.3 核心控件

- 每餐预算范围；
- 午餐 / 晚餐时间窗口；
- 正式用餐 ↔ 快速用餐；
- 最大排队时间；
- 预约优先；
- 本地店 ↔ 热门店；
- 是否接受便利店 / 简食作为赶路餐；
- 是否避免连续重复料理。

## 8.4 特殊需求

- 素食；
- 清真；
- 无猪肉；
- 儿童餐；
- 无障碍；
- 景观座位；
- 深夜营业。

# 9. 住宿偏好子菜单

## 9.1 首屏分成四块

```text
预算
位置优先级
住宿策略
必须设施
```

### 预算

显示每晚与全程估算：

```text
¥18,000–28,000 / 晚
预计全程 ¥54,000–84,000
```

### 位置优先级

支持排序：

- 靠近车站；
- 靠近每日第一站；
- 靠近夜间餐饮；
- 安静；
- 景观；
- 停车便利。

### 住宿策略

- 连住优先；
- 少换酒店；
- 温泉住宿；
- 经济型 / 舒适型 / 高级型；
- 酒店 / 民宿 / 公寓。

### 必须设施

- 早餐；
- 独立卫浴；
- 电梯；
- 洗衣；
- 行李寄存；
- 停车；
- 婴儿床；
- 无障碍；
- 大浴场 / 温泉。

## 9.2 房型设置

- 房间数量；
- 床型；
- 是否接受沙发床；
- 儿童同床；
- 连通房需求。

## 9.3 城市覆盖

长行程允许：

```text
全程默认
东京覆盖设置
京都覆盖设置
大阪覆盖设置
```

默认只展开全程设置，城市级覆盖保持折叠，避免复杂度暴露给普通用户。

## 9.4 已确认住宿保护

默认开启：

```text
保护已确认酒店
```

需要更换时，必须明确点击 `允许重新推荐`，并先显示受影响的预约与路线。

# 10. 更多行程设置子菜单

当前项目很多，不应在一个长页面内从上滚到下。推荐使用窄左侧分类栏 + 右侧内容区。

```text
┌──────────────┬──────────────────────────┐
│ 预算与节奏   │ 当前分类的设置内容       │
│ 移动与体力   │                          │
│ 每日时间     │                          │
│ 人流与天气   │                          │
│ 摄影与体验   │                          │
│ 行李与无障碍 │                          │
│ 锁定与预约   │                          │
└──────────────┴──────────────────────────┘
```

## 10.1 预算与节奏

- 日均预算滑轨；
- 全程预算摘要；
- 住宿 / 餐饮 / 活动预算占比；
- 很轻松 → 很紧凑；
- 每日主要地点估算；
- 连续高强度天数上限；
- 每几天安排恢复日。

## 10.2 移动与体力

- 少换乘；
- 少步行；
- 电车优先；
- 自驾优先；
- 出租车可用；
- 避免公交；
- 单日最大步行；
- 单次最大步行；
- 最大换乘数；
- 山路 / 夜间驾车；
- 停车便利；
- 行李移动约束。

## 10.3 每日时间

- 最早出发；
- 最晚回酒店；
- 午餐窗口；
- 晚餐窗口；
- 午休；
- 每日自由时间；
- 景点间缓冲；
- 固定不可安排时间。

## 10.4 人流与天气

- 避开人群；
- 热门优先；
- 最大排队时间；
- 早鸟 / 夜间错峰；
- 临时拥挤时自动替换；
- 雨 / 雪 / 高温 / 强风阈值；
- 户外活动自动降级；
- 船班 / 缆车风险策略。

## 10.5 摄影与体验

- 摄影优先；
- 日出 / 日落 / 夜景；
- Golden Hour；
- 观景方向；
- 拍照额外停留；
- 是否允许为了光线调整顺序；
- 本地体验比例；
- 自由探索比例。

## 10.6 行李与无障碍

- 行李件数与尺寸；
- 寄存；
- 酒店转运；
- 婴儿车；
- 电梯；
- 行动不便；
- 儿童设施；
- 医疗 / 休息要求。

## 10.7 锁定与预约

- 保留核心景点；
- 不改固定预约；
- 锁定某天；
- 锁定时间；
- 锁定酒店；
- 锁定交通；
- AI 不得自动删除；
- 取消截止前提醒。

该分类使用更明确的保护图标与说明，因为它直接决定重新规划边界。

# 11. 重新规划的预览层

点击 `预览 N 项变更` 后，不立即覆盖路线，先打开变化预览：

```text
┌──────────────────────────────────────┐
│ 本次将重新规划                       │
│ 第 2–4 天 · 9 个普通节点             │
├──────────────────────────────────────┤
│ 保持不变                             │
│ 2 项固定预约 · 1 家已确认酒店        │
├──────────────────────────────────────┤
│ 预计变化                             │
│ 步行减少约 2.1km                     │
│ 换乘减少 1 次                        │
│ Day 3 结束时间提前约 40 分钟         │
├──────────────────────────────────────┤
│ [返回修改] [生成预览路线]            │
└──────────────────────────────────────┘
```

生成预览后，地图以对比态显示旧 / 新路线，再由用户确认 `应用新路线`。

# 12. 底部信息栏统一骨架

## 12.1 顶栏

```text
┌ 第2天 · 4月11日 ─────────────────────────────┐
│ 行程  交通  预约²  天气!  吃住¹  体检²   ↑  │
└─────────────────────────────────────────────┘
```

- 左侧显示当前范围，但不重复完整的 `1日 / 3日 / 全日` 控件；
- Tab 文字 + 16px 线性图标；
- 只有需要处理时才显示数字 / `!`；
- 右侧提供临时展开按钮；
- 展开时面板覆盖地图向上延伸，不改变右栏尺寸。

## 12.2 激活态

激活 Tab 使用：

- 底部 2px 珊瑚色指示线；
- 极淡暖色背景；
- 文字加深；
- 不使用六个大号实心胶囊。

## 12.3 内容骨架

五个 Tab 全部复用同一 12 栏结构：

```text
┌────────────┬────────────────────────┬──────────────┐
│ 摘要区 2栏 │ 主信息画布 7栏         │ 提醒/动作 3栏│
└────────────┴────────────────────────┴──────────────┘
```

在较窄桌面可变为 `3 / 6 / 3`。

这样切换 Tab 时，用户不会感觉每一页都是不同产品。

## 12.4 卡片原则

- 默认不使用照片；
- 主卡圆角 14–16px；
- 边框低对比；
- 一张卡最多一个主动作；
- 主要数值 20–24px；
- 正文 12–13px；
- 最多显示 4 张主卡，更多内容横向滚动或展开；
- 未确定项使用虚线边框，不用红色；
- 状态必须有图标 + 文本。

# 13. 交通 Tab

## 13.1 一日模式

### 摘要区

```text
今日移动
2h35m
步行 6.8km
换乘 3 次
```

仅显示最重要的 3 个指标。

### 主信息画布：路线链

```text
酒店
  ─ 步行 12m · 0.8km ─
清水寺
  ─ 公交 24m · 1次换乘 ─
祇园
  ─ 电车 18m ─
锦市场
```

每一移动段卡显示：

- 起点 / 终点；
- 出发 / 到达；
- 方式；
- 时间与距离；
- 换乘；
- 费用；
- 无障碍 / 行李 / 停车提示；
- 是否锁定。

点击段：

- 地图只高亮该移动段；
- 自动缩放到起终点；
- 第二次点击或 `查看步骤` 打开详细换乘层。

### 提醒 / 动作区

只显示最高优先级事项，例如：

- 末班车；
- 站台变更；
- 需要提前购票；
- 停车困难；
- 步行超出偏好；
- 行李不便。

主按钮按问题变化：

```text
查看替代路线
购买车票
查看停车
```

## 13.2 三日模式

使用三条同结构对比行：

```text
D2  移动 2h10 · 步行 5.2km · 换乘2   正常
D3  移动 4h20 · 步行 3.0km · 跨城    偏高
D4  移动 1h40 · 步行 8.1km · 换乘1   步行偏高
```

每行内部用窄色带表示：

- 市内移动；
- 长距离移动；
- 步行；
- 等待 / 接驳。

右侧只显示三日最需要处理的一个问题。

## 13.3 全日模式

改为城市间主干链：

```text
东京 ─ 新干线 2h15 ─ 京都 ─ JR 30m ─ 大阪
```

显示：

- 航班；
- 长途铁路；
- 长途自驾；
- 渡轮；
- 机场连接；
- 租车 / 还车；
- 行李转运。

普通市内移动默认隐藏。

# 14. 预约 Tab

## 14.1 设计定位

预约 Tab 不是订单后台，而是：

> **与当前行程顺序一致的“待办 + 凭证”画布。**

## 14.2 一日模式

### 摘要区

```text
已完成 3 / 5
待处理 2
最近截止 18h
```

可使用小型环形进度，但数字必须同时存在。

### 主信息画布：时间顺序票券卡

每张使用轻量票券轮廓：

```text
10:00  清水寺门票
已出票 · 官方
凭证可用

12:30  午餐预约
待确认 · TableCheck
今日 18:00 前可取消
```

卡片字段：

- 时间；
- 项目；
- 类型；
- 状态；
- Provider；
- 人数；
- 订单号后 4 位；
- 取消 / 修改截止；
- 凭证状态。

Provider Logo 只用小型灰阶，不让第三方品牌抢视觉。

### 提醒 / 动作区

按紧急度排序：

1. 时间冲突；
2. 即将截止；
3. 待付款；
4. 待上传凭证；
5. 建议提前预约。

主动作示例：

- 完成预约；
- 打开凭证；
- 上传订单；
- 联系商家；
- 修改 / 取消。

## 14.3 三日模式

按 Day 分组，但保持时间顺序：

```text
D2  2项 · 全部完成
D3  3项 · 1项待处理
D4  1项 · 存在时间冲突
```

主画布可横向并排三列，每列只显示 2–3 个最关键票券。

## 14.4 全日模式

主视角切换为：

- 全程完成度；
- 按类型筛选；
- 预约截止时间轴；
- 尚未处理的高影响项目。

筛选：

```text
全部 / 交通 / 住宿 / 餐饮 / 景点
```

# 15. 天气 Tab

## 15.1 设计定位

天气 Tab 不复制天气 App，而是只回答：

- 行程时段会遇到什么；
- 哪些节点会受影响；
- 可以换成什么。

## 15.2 一日模式

### 摘要区

```text
18–25°C
降雨 60%
日落 18:21
```

天气数据尚不具备可靠逐小时预测时，应明确显示：

```text
详细预测尚未开放
当前为季节参考
```

不能伪装成实时精确预报。

### 主信息画布

上层是有效活动时段天气条：

```text
09:00  晴 19°
12:00  多云 23°
15:00  雨 22°
18:00  雨 20°
```

下层是“影响卡”：

```text
14:00–16:00 岚山
降雨概率较高 · 室外 2h
影响：拍摄、步行、渡船
```

### 提醒 / 动作区：备选方案

最多展示 2 个可以直接替换的备选：

```text
京都铁道博物馆
室内 · 增加移动 12m
[预览替换]
```

应用前必须显示：

- 替换哪个节点；
- 时间变化；
- 移动变化；
- 是否影响预约。

## 15.3 三日模式

三张天气日卡严格对齐三日行程：

```text
D2  户外适合度 82  晴
D3  户外适合度 38  午后雨
D4  户外适合度 74  多云
```

主结论应直接指出：

```text
建议把 D3 的户外活动与 D4 上午互换
```

并提供 `查看互换预览`，而不是只显示三天天气图标。

## 15.4 全日模式

只显示会改变行程结构的重要风险：

- 台风 / 暴雪 / 高温；
- 山区能见度；
- 船班 / 缆车停运风险；
- 影响跨城移动的强天气；
- 连续多日降雨区间。

普通晴雨不铺满全程。

# 16. 吃住 Tab

## 16.1 设计定位

住宿与餐饮放在同一 Tab 的理由不是“都是生活服务”，而是：

> **它们共同构成一天的空间锚点与时间锚点。**

## 16.2 一日模式

### 摘要区

```text
住宿 已确认
午餐 推荐区
晚餐 待预约
```

### 主信息画布

使用四张顺序卡：

```text
[今晚住宿] [午餐] [晚餐] [次日早餐/未安排]
```

#### 住宿卡

- 酒店 / 区域；
- Check-in / Check-out；
- 连住晚数；
- 是否已预约；
- 距离当天终点；
- 次日第一站便利度；
- 行李寄存 / 停车。

#### 餐饮卡

- 餐次与时间；
- 餐厅 / 推荐区域；
- 料理类型；
- 人均预算；
- 距离前后行程；
- 是否预约；
- 排队风险；
- 饮食限制匹配。

未确定卡使用暖灰虚线边框：

```text
晚餐尚未确定
祇园区域有 4 个顺路选择
```

不使用红色警告。

### 提醒 / 动作区

根据状态显示：

- 选择住宿区；
- 查看 4 家酒店；
- 选择午餐；
- 完成晚餐预约；
- 更换但保护原预约。

## 16.3 三日模式

采用上下两条轨道：

```text
住宿轨道：
D2 ───────── Hotel A ───────── D3   | D4 Hotel B

餐饮轨道：
D2 午 / 晚   D3 午 / 晚   D4 午 / 晚
```

连住酒店必须合并为一个跨日长卡，用户可以一眼看出：

- 连住几晚；
- 哪天换酒店；
- 换宿是否伴随长距离移动。

餐饮只显示已确定、已预约和明显缺口，不展示全部候选。

## 16.4 全日模式

以城市阶段展示：

```text
东京 3晚 · Hotel A
京都 3晚 · Hotel B
大阪 1晚 · 待确认
```

重点：

- 每城住几晚；
- 换酒店频率；
- 一晚换宿风险；
- 尚未确定的住宿夜；
- 特别餐饮预约。

普通每日午餐 / 晚餐默认折叠。

# 17. 体检 Tab

## 17.1 为什么替代“详细”

`详细` 没有明确任务，很容易不断加入地址、文件、联系方式、费用等杂项。

推荐将其改为：

> **行程质量体检与 AI 解释。**

地址、联系方式、凭证应分别进入节点详情和预约 Tab，不再塞进体检。

## 17.2 一日模式

### 摘要区

```text
综合状态
良好
2 项建议
```

不要使用无法解释的单一神秘分数；如显示分数，必须能展开查看构成。

### 主信息画布

上方 4 个 KPI：

- 活动时长；
- 移动时长；
- 步行；
- 预计费用。

下方使用时间构成条：

```text
景点 45% | 移动 18% | 餐饮 14% | 自由 13% | 缓冲 10%
```

### 提醒 / 动作区

按严重度显示最多 3 项：

- 营业时间风险；
- 时间缓冲不足；
- 步行超出偏好；
- 用餐缺口；
- 预算超出；
- 行李 / 无障碍问题；
- 固定预约冲突。

每项必须说明原因与影响：

```text
清水寺离开时间过晚
可能导致 17:00 的餐厅预约缓冲不足 12 分钟
```

动作：

```text
查看调整
忽略本次
锁定当前安排
```

## 17.3 三日模式

使用三日比较矩阵：

| 指标 | D2 | D3 | D4 |
|---|---:|---:|---:|
| 活动 | 6h20 | 8h40 | 4h50 |
| 移动 | 2h10 | 4h20 | 1h40 |
| 步行 | 5.2km | 3.0km | 8.1km |
| 强度 | 适中 | 高 | 适中 |

重点结论：

- 最忙 / 最松；
- 连续高强度；
- 折返；
- 住宿切换；
- 预约密度；
- 费用异常；
- 重复体验 / 重复料理。

可以给出跨日平衡建议，例如：

```text
把 D3 的一个景点移至 D4，可减少连续高强度并降低 45 分钟折返。
```

## 17.4 全日模式

显示：

- 总天数与城市数；
- 跨城次数；
- 换酒店次数；
- 最长移动日；
- 连续高强度区间；
- 停留过短城市；
- 尚未完成的关键预约；
- 预算结构；
- 行程准备完成度。

全日体检的重点是“结构是否合理”，不是把所有每日指标相加后展示。

# 18. 地图、右栏与底栏联动

继续使用统一 `tripItemId` / `segmentId`，不得由三个区域分别维护独立数据。

## 18.1 点击底部卡片

```text
底部卡片
→ selectedTripItemId / selectedSegmentId
→ 地图定位并高亮
→ 相关 Pin / 路线打开快速卡
```

## 18.2 点击地图对象

```text
地图对象
→ 底部保留当前 Tab
→ 滚动到对应卡片
→ 卡片边框加强 1.5 秒
```

例如：

- 点击公交路线 → 自动聚焦交通 Tab 中对应移动段；
- 点击酒店 → 自动聚焦吃住 Tab 的住宿卡；
- 点击已预约景点 → 自动聚焦预约 Tab 的票券卡。

不应强制切换 Tab，除非当前 Tab 完全无法表达该对象；此时先显示轻量提示：

```text
此项目的预约信息在“预约”中查看
```

## 18.3 跨 Tab 保留上下文

切换 Tab 时保持：

- 当前日期 / 三日窗口 / 全日范围；
- 当前选中节点；
- 地图视野；
- 右栏当前方案。

# 19. 视觉规格

## 19.1 色彩职责

- 珊瑚色：当前选择、主动作；
- 绿色：已确认 / 已预约；
- 黄色：需注意 / 即将截止；
- 红色：冲突 / 无法执行；
- 蓝灰：普通信息 / 推荐；
- 暖灰：未确定 / 暂无数据。

颜色永远配合图标与文字，不单独表达状态。

## 19.2 类别色

底部最多使用 5 个低饱和类别色：

- 景点 / 活动；
- 交通；
- 餐饮；
- 住宿；
- 空白 / 缓冲。

预约、天气和体检主要使用状态色，不再增加新的类别色体系。

## 19.3 排版

- 面板标题：14–15px / 600；
- 卡片标题：13–14px / 600；
- 正文：12–13px / 400–500；
- 辅助信息：11–12px；
- 关键数值：20–24px / 600；
- Tab：13px / 600；
- 问号说明图标比相邻正文约小 20%，仅 hover / focus 显示说明。

## 19.4 间距

- 面板内边距：16px；
- 卡片间距：10–12px；
- 卡片内边距：12–14px；
- 大区段间距：16–20px；
- 圆角：主面板 18–22px，内部卡 14–16px；
- 动画：140–220ms，优先 transform / opacity。

## 19.5 避免的视觉问题

- 不在底栏放大量照片；
- 不将每个状态都做成彩色胶囊；
- 不让六个 Tab 都有常驻红点；
- 不使用重阴影叠出三四层浮层；
- 不把右栏子菜单做成传统后台表单；
- 不同时出现两个主要 CTA；
- 不把“推荐”和“警告”使用同一种强调色。

# 20. 状态与空态

## 20.1 加载

使用与真实内容尺寸相同的 Skeleton，避免底栏切换时高度跳动。

## 20.2 无数据

空态必须给出原因与下一步：

```text
今天没有需要预约的项目
已加入的自由景点会继续保留在行程中
```

```text
今晚住宿尚未确定
已在地图标出 3 个顺路住宿区域
[查看住宿区域]
```

## 20.3 错误

局部失败不应让整个底栏消失：

```text
天气数据暂时无法更新
现有行程与备选方案仍可查看
[重试]
```

## 20.4 数据过期

外部预约、天气、交通状态需要显示更新时间：

```text
更新于 14:32
```

过期后使用文字提示，不只改变颜色。

# 21. 响应式与窄桌面

## 21.1 1440px 及以上

- 右栏完整摘要；
- 子菜单宽 460–480px；
- 底栏 `2 / 7 / 3`；
- Tab 显示图标 + 文字。

## 21.2 1280–1439px

- 子菜单宽 420–440px；
- 底栏 `3 / 6 / 3`；
- 摘要区减少到 2 个主指标；
- 主卡正文最多 2 行。

## 21.3 1024–1279px

- 右栏保持最低可用宽；
- 子菜单改为覆盖式侧滑层；
- 底栏第三动作区可折入 `更多`；
- Tab 仍显示短名称，不变成纯图标。

Mobile 不直接压缩桌面 Planner，应另做移动端结构。

# 23. 验收标准

## 右栏

- [ ] 默认态在 25% 宽右栏中无需内部滚动即可看到全部 4 个入口与操作按钮；
- [ ] 同行人和日期共享一张基础摘要卡，但热区清晰；
- [ ] 玩 / 吃 / 住 / 更多条件的行高、摘要、箭头完全统一；
- [ ] 子菜单不改变地图、底栏和三方案区域尺寸；
- [ ] Level 3 不再打开额外第三层浮窗；
- [ ] 修改偏好后不会立即触发路线重算；
- [ ] 重新规划前可看受影响日期、受保护预约和主要变化。

## 底栏

- [ ] 五个辅助 Tab 使用同一 `摘要 / 主画布 / 动作` 骨架；
- [ ] 一日、三日、全日只改变数据颗粒度，不改变基本交互语言；
- [ ] 点击卡片可定位并高亮地图对象；
- [ ] 交通 Tab 能直观看出移动段与高风险段；
- [ ] 预约 Tab 能直观看出完成度、截止与凭证；
- [ ] 天气 Tab 必须提供“影响对象”和“可执行备选”，而不只是预报；
- [ ] 吃住 Tab 能一眼识别已确认、推荐与缺口；
- [ ] 体检 Tab 不再承载地址、联系方式等杂项；
- [ ] 未确定、注意、冲突、已确认均不只依靠颜色表达；
- [ ] 默认底栏内不使用大图，保持地图为页面视觉主体。

# 24. 最终推荐

右栏与底栏不应继续通过“增加更多小卡片”来表现功能完整度。

最终视觉方向应是：

```text
右栏默认态
= 少量摘要 + 明确入口 + 可控重新规划

右栏子菜单
= 上下文明确、分组清楚、可预览影响的设置工作层

底部辅助 Tab
= 每个 Tab 只解决一个核心问题
= 同一布局骨架，不同数据叙事

体检
= TravelAssist 区别于普通地图与 OTA 的核心价值入口
```

其中最重要的三项改动是：

1. 将同行人 / 日期压缩为一张基础摘要卡，把空间让给清晰的设置行；
2. 将“更多设置”重构为 7 类导航，而不是无限向下滚动的长表单；
3. 将“详细”改为“体检”，让 AI 的价值集中在可解释、可执行的行程质量判断上。
