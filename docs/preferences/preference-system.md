# TravelAssist 偏好系统设计书

> 状态：v0.2 / 本轮对话结论已整合
>
> 适用范围：Step 2 偏好录入、更多兴趣、更多行程设置、特别要求、AI 自然语言解析、景点候选排序、行程生成与重规划
>
> 核心原则：**用户只负责表达“想要什么 / 不要什么 / 不能接受什么”，系统负责计算日期、天气、季节、同行人适配、POI 属性、拥挤度、时段与路线可行性。**

---

## 1. 设计目标

偏好系统必须同时满足两类用户：

- 普通用户：不想研究复杂参数，希望几十秒内表达方向并快速得到可用行程。
- 高级用户：希望进一步控制步行、换乘、时段、景点类型、拍照、预算、无障碍等细节。

因此前台采用渐进式结构：

```text
主界面（一级）
  └─ 二级菜单
      └─ 三级菜单
```

但必须明确：

**前台三级菜单 ≠ KANZAKI 43 个后台字段。**

43 个字段属于后台 POI / 行程评分维度。用户只看到容易理解的产品语言，系统再将用户选择映射成后台权重、阈值或硬约束。

---

## 2. 本轮最终结论

### 2.1 主界面表示什么

主界面负责：

> **快速表达“我这次大概喜欢什么、想怎么玩”。**

主界面只显示普通用户一眼就能理解、且必须由用户本人表达的主观偏好。

不要求用户理解数据库分类，不要求逐项打分，也不把未选择项自动解释为“不喜欢”。

### 2.2 二级菜单表示什么

二级菜单负责：

> **对一级方向进行进一步细化。**

例如用户选择“自然风景”，二级菜单再询问更偏好山岳、湖泊、海岸、庭园还是季节景观。

普通用户可以不打开二级菜单。

### 2.3 三级菜单表示什么

三级菜单只保留两类内容：

1. **精细兴趣**：例如红叶、街头摄影、铁道摄影、日归温泉。
2. **可执行限制 / 明确条件**：例如不坐船、避免楼梯、最晚 21:00 结束。

三级菜单不应该为了“分类完整”继续堆砌抽象标签。

---

## 3. 偏好信息的三种来源

整个系统必须区分三种信息来源。

### 3.1 用户主动选择

系统不能可靠替用户决定的内容，例如：

- 喜欢自然还是历史
- 偏经典还是偏小众
- 想轻松还是充实
- 愿意走多少路
- 是否喜欢摄影、动漫、铁道、夜间活动
- 是否有明确必去地点
- 是否拒绝某种交通方式
- 是否需要轮椅 / 婴儿车适配

### 3.2 系统自动计算

可以由客观信息可靠推导的内容，不重复询问用户，例如：

- 春 / 夏 / 秋 / 冬
- 雨天 / 炎热 / 寒冷 / 下雪
- 上午 / 白天基础适配
- POI 是否属于经典地标
- POI 是否小众、独特、地方特色
- POI 对家庭 / 老人 / 情侣 / 独行的适配程度
- 实际拥挤度与排队风险
- 当前天气下的景点适配程度

### 3.3 POI / 系统原始属性

这些是景点或系统本身的数据，而不是用户偏好，例如：

- 一个景点的 `walking = 7`
- 一个景点的 `wheelchair = 3`
- 一个景点的 `iconic = 9`
- 一个景点的 `weather_sensitive = 8`

用户设置决定系统如何使用这些属性，而不是让用户自己填写这些属性。

# 4. Step 2 主界面：用户需要看到的内容

## 4.1 景点兴趣：8 个一级入口

Step 2 “您的兴趣”建议固定展示以下 8 个大项目：

1. **自然风景**
2. **历史文化**
3. **城市漫游**
4. **美食咖啡**
5. **艺术展览**
6. **购物潮流**
7. **乐园娱乐**
8. **温泉放松**

建议交互：

- 默认只需要“选中 / 未选中”。
- 可选增加“特别想要”，但不要求每一类打 5 档或 6 档分数。
- 不强制用户必须选满固定数量。
- 提供“还没想好，请为我推荐”。
- 未选择 ≠ 不喜欢。

### 4.1.1 为什么摄影不作为一级景点类别

`photo` 属于横向体验目的，而不是独立景点类型。

例如：

```text
自然 + 摄影 → 风景摄影
城市 + 摄影 → 街头摄影
建筑 + 摄影 → 建筑摄影
夜间 + 摄影 → 夜景摄影
```

因此摄影放入“更多兴趣”，后台仍保留 `photo` 维度。

### 4.1.2 为什么 local / unique / hidden / iconic 不展示为兴趣类别

这 4 项是景点特征，不是用户容易直接填写的景点类型。

前台只需要一个“景点取向”：

```text
经典为主 / 混合推荐 / 小众为主
```

后台再映射到：

- `iconic`
- `hidden`
- `unique`
- `local`

---

## 4.2 旅行风格：主界面只显示 3 项

Step 2 “您喜欢怎么玩”只保留三个高价值、容易理解且直接影响路线的选项。

### 4.2.1 行程节奏

```text
轻松 / 适中 / 充实
```

影响：

- 每日景点数量
- 单点停留时间
- 连续活动时间
- 休息次数
- 路线缓冲
- 连续移动时间

关联后台：

- `relax`
- `rest`
- `walking`
- `physical`

### 4.2.2 景点取向

```text
经典为主 / 混合推荐 / 小众为主
```

主要关联：

- `iconic`
- `hidden`
- `unique`
- `local`
- `adventure`

### 4.2.3 步行接受度

```text
少走 / 适中 / 愿意多走
```

影响：

- 可接受 `walking` 区间
- `physical` 的部分阈值
- 路线步行距离
- 换乘策略
- 是否建议出租车
- 同等候选时的景点替换

### 4.2.4 不再作为首屏滑轨的旧项目

以下能力不删除，但移入“更多行程设置”：

- 少点深度 ↔ 多点覆盖
- 计划明确 ↔ 随性自由
- 性价比 ↔ 舒适

其中“性价比 ↔ 舒适”不再作为单一对立轴，应拆成总体预算与花费优先级。

# 9. 特别要求 / 硬约束

特别要求必须有清晰、容易找到的入口，不能埋在普通兴趣菜单最深层。

## 9.1 无障碍与同行需求

### 轮椅

- 轮椅适配
- 无障碍路线
- 电梯 / 坡道
- 无障碍厕所

### 婴儿车

- 婴儿车适配
- 避免长楼梯
- 需要电梯
- 方便上下车

## 9.2 体力限制

### 步行限制

- 减少连续步行
- 限制每日步行量
- 增加休息点

### 地形限制

- 避免台阶
- 避免陡坡
- 避免登山

### 休息安排

- 午休
- 固定休息
- 连续活动时间限制

## 9.3 必去 / 已确定安排 / 排除

### 必须安排

- 必去景点
- 已预约景点
- 已预约餐厅
- 已确认活动

### 明确排除

- 不去某类景点
- 不去指定地点
- 不参加指定活动

> “必须安排”不作为普通兴趣评分的最高一档。兴趣与具体必去地点必须分开保存。

# 10. 同行人员的处理方式

同行人员不属于普通旅行兴趣，应由已有同行人员设置独立输入。

基础类型可包括：

- 成人
- 儿童
- 婴儿
- 老人

底层至少保存人数，后续可按产品需要补年龄段。

## 10.1 系统可以自动做的事情

例如儿童同行：

```text
同行人员包含儿童
↓
family 适配权重提高
互动体验候选权重提高
儿童友好设施参与排序
```

老人同行：

```text
同行人员包含老人
↓
senior 适配分参与排序
系统提示确认步行 / 台阶需求
```

## 10.2 系统不能擅自做的事情

以下推断禁止直接变成硬约束：

```text
有儿童 ≠ 一定使用婴儿车
有老人 ≠ 禁止徒步
情侣 ≠ 必须安排浪漫景点
独行 ≠ 不安排高级餐厅
```

同行人员只负责产生适配权重与必要提示；实际硬限制需要用户明确确认。

# 12. 43 字段：哪些展示，哪些计算

| 字段组 | 是否直接展示 | 主要来源 / 用法 |
|---|---|---|
| scenery / history / architecture / food / shopping / nature / onsen / art / entertainment | 否，使用前台 8 个兴趣入口表达 | POI 固有评分 + 用户兴趣映射 |
| photo | 通过“更多兴趣 → 摄影优先”表达 | POI 摄影价值 + 用户横向兴趣 |
| night | 通过夜间体验 / 夜景意愿表达 | POI 夜间价值 + 营业时间 + 用户时间偏好 |
| local / unique / hidden / iconic | 不直接展示字段名 | POI 属性 + 经典/小众取向 |
| family / senior / couple / solo | 不作为兴趣菜单 | POI 适配属性 + 同行人员结构 |
| relax / adventure / educational / interactive / rest | 部分通过旅行风格表达 | POI 属性 + 行程风格 |
| walking / physical | 用户选“接受度”，不填景点数值 | POI 负担 + 停留时间 + 路线 + 用户阈值 |
| crowd / queue | 用户选容忍度，实际值自动计算 | POI 历史/实时数据 + 日期时段 |
| wheelchair / stroller | 在特别要求中明确选择 | POI 无障碍属性 + 用户硬约束 |
| morning / daytime | 不常规展示 | POI 最佳时段 + 营业时间 + 行程时间 |
| sunrise / sunset | 用户可表达特殊意愿 | 日出日落时间 + POI 适配 + 用户偏好 |
| rain / heat / cold / snow | 不常规询问 | 天气预报 + POI 天气适配 |
| weather_sensitive | 不展示 | POI 固有属性 |
| spring / summer / autumn / winter | 不询问用户 | 旅行日期 + 地点 + POI 季节属性 |

# 13. 自动计算关系

## 13.1 季节

```text
旅行日期
+ 目的地
+ POI 季节属性
↓
spring / summer / autumn / winter
↓
季节性景点候选调整
```

例如用户 11 月前往京都，系统自然提高 `autumn` 相关 POI 的适配，不需要再询问“是否喜欢秋季”。

如果用户明确选择“红叶”，则这是额外的用户兴趣权重，而不是季节本身。

## 13.2 天气

```text
天气预报
+ POI rain / heat / cold / snow / weather_sensitive
+ 用户硬约束
↓
当天景点适配分
↓
必要时替换备选景点
```

## 13.3 时段

```text
营业时间
+ 日出日落时间
+ POI morning/daytime/sunrise/sunset/night
+ 用户最早出发 / 最晚结束
↓
推荐访问时段
```

## 13.4 人群适配

```text
同行人员结构
+ POI family/senior/couple/solo
+ 用户确认的实际限制
↓
人群适配分
```

## 13.5 经典 / 小众

用户选择：

```text
经典为主
```

系统倾向：

```text
iconic ↑
local 适度参与
hidden 权重下降
```

用户选择：

```text
小众为主
```

系统倾向：

```text
hidden ↑
unique ↑
local ↑
iconic 权重适度下降
```

# 14. 步行与体力不能只看景点静态分

`walking` 与 `physical` 是景点基础属性，但行程中的实际负担必须结合停留时间和路线计算。

例如同一个清水寺类景点：

```text
POI walking = 7
建议停留 90 分钟
```

如果行程只安排 30 分钟，不能简单把完整 90 分钟的疲劳值直接照搬；同时 30 分钟也可能导致“行程合理性不足”。

因此需要区分：

```text
POI 基础 walking / physical
× 实际停留时间修正
+ 到达/离开路线负担
+ 连续活动累积
+ 同行人员适配
+ 用户步行接受度
↓
实际行程疲劳值
```

同时景点应保存：

- 最低合理停留时间
- 推荐停留时间
- 可扩展停留时间（如适用）

当实际安排低于最低合理停留时间时，行程合理性应被扣分或直接触发修正，而不是仅通过降低疲劳来“通过”。

---

# 15. 偏好状态必须区分

系统至少区分以下状态：

## 15.1 长期用户偏好

例如长期更喜欢自然、长期不喜欢购物。

是否自动继承到新旅行仍需产品层最终确认；即使继承，也必须允许本次旅行覆盖。

## 15.2 本次旅行偏好

例如：

- 这次想看红叶
- 这次带父母所以想轻松一点
- 这次以美食为主

## 15.3 软偏好

尽量满足，但必要时可以取舍，例如：

- 小众为主
- 少换乘
- 美食优先

## 15.4 硬约束

默认不能违反，例如：

- 不坐船
- 必须轮椅可达
- 必须去某个已预约景点
- 21:00 前结束

若硬约束之间冲突，系统不能静默忽略，必须提示并解释。

## 15.5 未表达

用户未选择某项时，必须保存为“未知 / 未表达”语义，而不是自动转成“不喜欢”。

---

# 16. AI 与设置面板共用同一套状态

AI 对话和 UI 设置不能成为两套系统。

例如用户自然语言输入：

> 京都三天，想吃好一点、拍拍照，不要太累，不去乐园。

应解析为概念上的结构化状态：

```text
interests.food = preferred
interests.photo = preferred
tripStyle.pace = relaxed
exclusions.entertainment.themePark = true
```

随后：

1. Step / Planner 设置摘要同步显示。
2. 景点候选重新计算。
3. 地图与时间轴重新规划。
4. AI 解释主要变化。

反过来，用户在设置面板修改参数后，AI 也必须读取最新状态。

- 摄影

- 必去
- 已预约
- 明确排除

# 19. 产品体验原则

1. **系统需要的参数多，不代表用户需要填写的参数多。**
2. **大项目用于快速理解，不追求数据库分类完整性。**
3. **二级菜单只在用户有兴趣时展开。**
4. **三级菜单必须具有明确推荐价值或执行价值。**
5. **日期、天气、季节、时段等能可靠计算的内容不要重复询问。**
6. **同行人员只能产生适配权重与提示，不能未经确认变成硬约束。**
7. **未选择不是“不喜欢”。**
8. **兴趣、必去和硬限制必须分开保存。**
9. **默认值必须可见、可修改，不能伪装成用户明确表达的长期偏好。**
10. **AI 与 UI 使用同一份结构化状态。**
11. **推荐结果应允许直接修正，而不是迫使用户重填表单。**
12. **没有可靠数据支撑的细分标签不要仅为显得专业而上线。**
