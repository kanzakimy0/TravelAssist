# 偏好系统设计

> 状态：v0.1 / 结构已确定，完整分类仍在持续补充

## 1. 目标

偏好系统需要同时满足两类用户：

- 普通用户：不想填复杂表单，只希望快速生成不错的行程。
- 高级用户：希望精确控制步行、换乘、交通方式、景点类型、拍照等细节。

因此采用三级结构：

```text
大项目
  └─ 中项目（快速设置）
      └─ 小项目（详细设置）
```

核心原则是 **默认简单、逐层展开、AI 与表单共用同一套参数**。

---

## 2. 展示层级

### 第一层：摘要

只显示少量关键状态，例如：

- 日期
- 同行人
- 旅行节奏
- 移动偏好概要
- 景点喜好概要

### 第二层：中项目

中项目是主要设置层。

每个中项目应该有：

- 当前状态摘要
- 快速设置
- 展开入口

### 第三层：小项目

小项目提供具体限制与细节。

普通用户可以永远不打开这一层。

---

## 3. 同行人优先

同行人信息应放在偏好设置前部，因为它会影响大量下游推荐。

当前已讨论类型：

- 成人男性
- 成人女性
- 小孩
- 婴儿

建议底层至少保存数量，而不是只保存“家庭 / 情侣”等标签。

系统可以根据同行人组合推断旅行场景，例如：

- 亲子旅行
- 情侣旅行
- 家庭旅行
- 朋友旅行

但推断结果只能作为推荐辅助。

### 同行人可能影响

- 步行强度
- 换乘次数
- 休息间隔
- 儿童友好设施
- 婴儿车可达性（后续数据允许时）
- 用餐时间
- 夜间活动
- 住宿区域

---

## 4. 大项目建议结构

以下为当前可用的一级分类框架；其中部分细分类仍需继续冻结。

```text
偏好
├─ 同行人
├─ 日期与行程条件
├─ 移动 / 交通
├─ 景点与活动
├─ 餐饮
├─ 住宿
├─ 行程节奏
└─ 其他限制
```

说明：一级分类名称后续可以调整，但产品应保持“少量大类 + 可展开详细项”的结构。

---

## 5. 移动 / 交通

移动偏好是已经讨论较深入的一类。

### 中项目快速设置示例

- 轻松优先
- 平衡
- 效率优先
- 少换乘
- 少步行

### 已明确的小项目示例

- 少换乘
- 少步行
- 不乘坐公共交通
- 不乘坐公交
- 不乘坐游船

未来可根据数据源继续加入具体交通方式限制，但在设计确认前不要由 Codex 自行扩充业务枚举。

### 参数冲突

系统必须能处理冲突，例如：

```text
少步行 + 不乘公共交通
```

这种组合可能不可同时满足。

处理原则：

1. 不静默忽略用户条件。
2. 给出冲突提示。
3. AI 解释需要取舍的原因。
4. 必要时询问用户哪个条件优先。

---

## 6. 景点与活动

景点设置不能只停留在“寺庙 / 博物馆 / 公园”这种传统类别。

需要同时考虑：

- 景点类别喜好
- 活动形式
- 行为目的
- 强度
- 时间适配

当前明确应支持更细的行为偏好，例如：

- 拍照

### 快速设置

快速层只显示“喜好”，避免复杂评分表。

例如用户可以快速表达：

- 很喜欢
- 喜欢
- 一般
- 不喜欢

具体量化实现由后续技术设计决定。

### 详细设置方向

未来可以继续扩充：

- 必去 / 希望去 / 可去 / 不去
- 拍照偏好
- 室内 / 室外倾向
- 热门 / 小众倾向
- 文化 / 自然 / 购物 / 娱乐等类别

其中尚未在设计会话中冻结的项目应视为候选，不直接进入正式枚举。

---

## 7. 餐饮

餐饮应同时参与行程时间和地理路线，而不是独立餐厅搜索。

当前页面方向：

- 地图先显示推荐午餐 / 晚餐区域
- 用户需要时再展开具体餐厅候选

后续偏好可考虑：

- 菜系
- 预算
- 用餐时间
- 排队容忍度
- 儿童友好
- 特殊饮食限制

上述详细枚举尚未冻结。

---

## 8. 住宿

住宿同样先考虑“区域合理性”，再考虑具体酒店。

偏好系统最终应能影响：

- 推荐住宿区域
- 每日交通成本
- 换酒店次数
- 夜间活动便利性
- 次日出发效率

具体星级、预算、房型等枚举尚待确认。

---

## 9. 行程节奏

系统需要有一个高层节奏概念，用来帮助 AI 和推荐器协调大量小参数。

候选方向：

- 轻松
- 平衡
- 紧凑

节奏不能简单等同于景点数量，还应结合：

- 步行
- 移动时间
- 换乘次数
- 停留时间
- 午餐 / 晚餐时间
- 同行人构成

具体算法尚未冻结。

---

## 10. AI 与偏好同步

AI 对话和设置面板不能是两个系统。

例如用户说：

> 我们带一个小孩，不要走太多路，也别换太多次车。

系统应转换为结构化状态，例如概念上：

```text
companions.child = 1
mobility.lessWalking = true
mobility.fewerTransfers = true
```

随后：

1. 设置面板同步显示。
2. 行程生成器读取新状态。
3. 地图 / 时间轴重新计算。
4. AI 解释主要变化。

反过来，用户直接在设置面板修改参数后，AI 也必须知道最新状态。

---

## 11. 数据设计原则

偏好需要区分：

### 用户长期偏好

例如长期不喜欢某种活动。

### 本次旅行偏好

例如这次因为带婴儿而减少步行。

### 硬限制

不能违反，例如明确表示不乘某种交通方式。

### 软偏好

尽量满足，但必要时可以取舍。

后续技术设计应明确优先级，避免所有偏好都被当成不可违反条件。

- [x] 交通设置包含少换乘、少步行等方向。

- 餐饮、住宿完整偏好项目。
