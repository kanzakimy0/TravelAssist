# 两人开发分工与接手机制

> 状态：v0.1 / 当前开发协作基线

## 1. 基本比例

项目按两人协作：

- A：约 70%
- B：约 30%

比例代表主要工作量分配，不代表模块永久归属。

## 2. A 的主要职责

A 优先负责：

- 总体产品与技术架构
- 核心 Trip State / Preference State
- AI 行程生成主流程
- 地图与行程核心集成
- 关键数据结构
- 后端核心 API
- develop 集成
- 发布与版本控制
- 高风险 / 高耦合模块

## 3. B 的主要职责

B 优先负责：

- 可独立页面
- 可独立 UI 组件
- 设置面板子模块
- 测试
- Mock Data / Master Data 整理
- 文档同步
- Bug 修复
- 边界清楚的 API / 工具模块
- A 因时间或能力无法完成时的接手任务

## 4. 任务必须 Issue 化

所有正式开发工作都建立 GitHub Issue。

Issue 最少包含：

- 目标
- 范围
- 不包含内容
- 验收条件
- 设计文档链接
- 负责人
- Codex 提示

不要只在聊天里说“你做这一块”。

## 5. 分支规则

```text
main
└─ 稳定 / 发布

develop
└─ 日常集成

feature/a-xxx
└─ A 功能

feature/b-xxx
└─ B 功能

fix/xxx
└─ Bug 修复
```

每个功能分支尽量对应一个 Issue 或一个清晰工作单元。

## 6. 正常协作流程

```text
设计文档冻结
  ↓
建立 Issue
  ↓
从 develop 建 feature 分支
  ↓
开发 / Codex 辅助
  ↓
自测
  ↓
Pull Request → develop
  ↓
Review / CI
  ↓
合并
```

稳定阶段：

```text
develop
  ↓
发布检查
  ↓
main
```

## 7. A 无法按时完成时

不要等到最后再整块交接。

### 接手条件

出现以下情况可以把部分任务交给 B：

- A 预计赶不上阶段节点。
- 技术问题卡住且 B 可以并行尝试。
- 某模块可以拆成独立组件 / API / 测试。
- A 需要集中处理更高优先级核心模块。

### 交接步骤

1. A 先提交当前可运行代码。
2. 在 Issue 记录已完成 / 未完成内容。
3. 把未完成工作拆成尽量独立的子 Issue。
4. 写清输入、输出、接口和验收条件。
5. B 从最新 `develop` 或指定分支开始，不依赖 A 本机文件。
6. B 完成后通过 PR 合回。

## 8. 接手设计原则

为提高可接手性：

- 少做超大分支。
- 一项任务不要持续数周不提交。
- 公共接口先确定再并行。
- Mock 数据与类型定义尽早提交。
- 文档跟代码一起更新。
- 未完成代码可以提交为 Draft PR，避免只存在本机。

## 9. AI 工具分工

A 可使用更高能力的 ChatGPT / Codex 处理：

- 架构
- 跨模块重构
- AI Agent / Tool 流程
- 复杂调试
- 集成

B 可使用 ChatGPT / Codex 处理：

- 页面组件
- 单模块实现
- 测试
- 文档
- 数据整理
- Bug 定位

AI 工具不能代替设计冻结。实现前必须先读对应 `docs/`。

## 10. PR 要求

PR 至少写：

- 解决哪个 Issue
- 改了什么
- 如何测试
- 截图 / UI 变化（如果适用）
- 已知问题
- 是否修改产品规则

如果实现中发现设计冲突，不要在代码里偷偷决定，应回到 Issue / docs 更新。

## 11. 责任动态调整

70/30 不是固定到每周。

可以出现：

- 某周 A 90 / B 10
- 某阶段 A 60 / B 40

但长期总量仍以 A 主导、B 辅助为基线。
