# TravelAssist 开发 WBS

> 状态：v0.1  
> 更新日期：2026-09-04  
> 适用：双人开发（A 约 70% / B 约 30%）  
> 当前策略：Web MVP 优先，App 在核心业务与数据结构稳定后启动。

## 1. 执行原则

1. GitHub Issue 是开发任务的唯一执行入口。
2. 每个 Issue 原则上只对应一个可独立验收的结果。
3. 功能分支从 `develop` 创建，完成后通过 PR 合并回 `develop`。
4. `main` 只接收稳定、可演示或可发布版本。
5. A 负责核心架构、关键状态、AI 流程、集成与发布；B 负责可独立拆分的 UI、组件、测试、资料与接手任务。
6. A 无法完成或进度落后时，优先把边界清晰的 Issue 整体转交 B，不拆成“半个任务”。
7. Codex/GPT 实现前必须先读对应设计文档；未确定的产品规则不得自行补全。

## 4. Phase 2 — MVP 功能化

后续在 Phase 1 骨架稳定后拆 Issue：

- 登录 / 用户资料 / 行程保存
- 真实地图与地理编码服务
- 景点 / 餐饮 / 住宿候选数据源
- 交通方式与移动时间计算
- AI 重新规划与局部修改
- 多方案评分与解释
- 分享 / 导出
- 错误处理、缓存、日志、监控
- Beta 部署

## 5. A / B 动态接手机制

### 正常情况

- A：核心架构、状态、AI、地图核心、集成。
- B：首页、设置 UI、候选方案 UI、响应式、测试与资料。

### A 进度不足时

优先转交给 B：

1. 已定义 Props / Schema 的 UI 组件。
2. 已有 Mock Data 的页面模块。
3. 测试、Story/示例、响应式修正。
4. 数据整理与静态配置。
5. 文档同步。

A 保留：

- 跨模块状态与数据结构最终决定。
- AI / Backend 边界。
- 合并冲突与发布集成。

## 6. 每个 Issue 的完成定义（DoD）

- [ ] 实现内容与 Issue 范围一致。
- [ ] 未擅自新增产品规则。
- [ ] lint / typecheck 通过。
- [ ] 关键逻辑有基础测试或明确人工验收步骤。
- [ ] UI 任务包含桌面主要尺寸检查。
- [ ] 相关 Markdown 文档已同步。
- [ ] PR 描述中写明：做了什么、如何验证、仍有哪些限制。

## 7. Codex / GPT 通用执行命令

```text
你正在开发 TravelAssist。

先阅读：
1. README.md
2. CONTRIBUTING.md
3. docs/README.md
4. 与当前 Issue 对应的设计文档
5. 当前 GitHub Issue

要求：
- 只实现 Issue 范围。
- 不自行决定文档中标记为“未确定”的产品规则。
- 优先复用现有组件与类型。
- 修改前说明计划修改的文件。
- 完成后运行项目已有的 lint、typecheck、test。
- 输出：修改摘要、验证结果、仍未解决的问题。
```
