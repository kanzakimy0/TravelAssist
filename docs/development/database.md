# Database foundation — TASK-015-A

## Boundaries

Supabase PostgreSQL is the database. `supabase/migrations/*.sql` is the **only**
formal schema history and Supabase CLI is its runner. Drizzle/postgres.js is the
trusted server query/transaction layer. The empty schema export intentionally
does not define users, profiles, preferences, companions, trips, places or bookings.
No page uses the database yet; browser trip saving remains unchanged.

The frozen bootstrap plan takes precedence over legacy key examples in the older
database standards. No Auth cookies/session, `@supabase/ssr`, RLS policies, client
factory framework, remote project or production migration is implemented here.
The installed Supabase SDK is reserved for later typed clients after genuine
Local types and the relevant auth/data contracts exist.

## Requirements and local commands

- Node 24 (`.nvmrc`) and npm; install with `npm ci`.
- A working local Docker-compatible runtime. This task does not install one.
- No Supabase login, cloud project, personal token, linked project or cloud DB URL.

```bash
npx supabase --version
npm run db:start
npm run db:status
npm run db:reset
npm run db:types
npm run typecheck
npm run db:stop
```

Configuration was generated by pinned Supabase CLI 2.116.0, with stable project ID
`travelassist`, PostgreSQL 17, local site URL `http://127.0.0.1:3000`, no extra auth
redirects and no enabled experimental pg-delta or vector storage. Other built-in
stack defaults are not application Auth/Storage implementations.

The project ID and ports identify a **shared local stack across worktrees**. Do
not operate competing checkouts at the same time. Before reset, confirm that the
local `travelassist` stack belongs to this task and back up any valuable data.
Reset erases this local database and replays SQL + the empty seed; it never targets
Staging/Production. Stop preserves volumes (no `--no-backup`).

Wrappers accept no extra flags and reject remote Docker endpoints. Only local Unix
sockets and Windows named pipes are allowed. Cloud/PG credentials are removed from
the child environment. CLI credential tables and raw errors are withheld; status
only prints recognized loopback service URLs. On a failure, inspect locally without
copying raw credential-bearing CLI output into Git, Issue, PR or logs.

## Current runtime limitation

The implementing workstation has no usable Docker. Static commands are not proof
of DB startup/reset. The migration directory currently contains **zero SQL files**;
PostGIS has not been enabled or verified. Do not add untested PostGIS DDL to pretend
this acceptance condition passed. No handwritten generated database type placeholder
is included. See the TASK-015 Result for the precise validation status.

When a supported Local runtime becomes available, complete startup/reset first,
then verify any minimal PostGIS migration using an actual extension/version query
and another reset. Generate and commit real types; only then can runtime acceptance
be considered complete. This follow-up does not authorize business schemas.

## Query and generated-type interfaces

- `getDb()` is server-only and lazy. Importing the module does not require
  `DATABASE_URL`, open a connection, run SQL or probe a service. Missing/invalid
  configuration throws a redacted error only when called. `prepare: false` supports
  the transaction pooler contract. Callers must authorize requests themselves.
- `closeDb()` is for explicit test/process shutdown, not per-request cleanup.
  A module-scoped client is reused until closed; hot reload or separate processes
  can have separate instances. Production pooling refinement belongs to API work.
- `drizzle.config.ts` describes empty mappings/introspection output only and has no
  credentials. Do not use it to generate or run a second migration history.
- `db:types` obtains `public` schema types from the pinned Local CLI, adds a
  generated notice, formats and atomically replaces `src/types/database.generated.ts`.
  A failed command/parse leaves previous types intact. Identical output is a no-op.
  Temporary fixture types in unit tests are not application generated types.

## Environment contract

Only empty placeholders belong in `.env.example`:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=
SUPABASE_URL=
SUPABASE_SECRET_KEY=
DATABASE_URL=
```

Publishable is the future browser key. Secret key and DATABASE_URL are server-only;
never add public aliases or legacy anon/service_role aliases. Real URLs/keys/passwords
belong in private local/deployment configuration, not Git. Existing Mapbox variables
are unchanged. An ordinary build needs none of these values.

## Verification and migration workflow

```bash
npm ci
npm run test:db-foundation
node --experimental-strip-types --test tests/*.test.mjs
npm run lint
npm run typecheck
npm run build
npm run format:check
git diff --check
```

Run existing tests explicitly: this repository has no generic `test` script.
Generated types, actual reset and PostGIS checks cannot be replaced by static tests.
For SQL changes use timestamped Supabase migrations, update ORM mappings/types in
the same reviewed PR, and never rewrite merged/shared migration history. Production
uses reviewed forward migrations; never Dashboard-only changes or `drizzle-kit push`.

Stable drizzle-kit's deprecated loader brings an old esbuild dev-server advisory.
The narrow `@esbuild-kit/core-utils → esbuild 0.25.12` override fixes that transitive
dependency without changing Next/React/TypeScript. CLI/config-loader smoke and the
lockfile audit must be repeated when upgrading the tool.

## Delivery safety

The repository auto-creates and attempts to merge feature PRs on push. Initial
publication uses a commit with `[skip ci]`, then explicitly creates a Draft PR.
Verify Draft before every subsequent push; never mark Ready or enable auto-merge.
Skipped workflows are **not** successful CI validation. Existing automation is
unchanged. Result/WBS/Issue must distinguish static review from runtime acceptance.
