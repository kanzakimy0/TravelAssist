## PR #406 — Planner Save/Read

### Positive findings

The implementation correctly:

- reuses the accepted Trip repository;
- keeps RLS / Auth server-side;
- uses Trip + Plan revision CAS;
- validates Canonical Trip payloads;
- keeps browser/UI/detail-draft state out of Canonical persistence;
- preserves local work on stale server reads/writes;
- protects against late hydrate / late acknowledgement;
- includes real Local Supabase/Auth/RLS/CAS tests.

### Blocking finding

Canonical-data integrity issue:

1. `plannerTripFromCanonical()` creates fallback UI coordinates when a Canonical place has no coordinates.
2. The fallback is intentionally visual-only.
3. `canonicalPlace()` serializes current Planner coordinates for newly added items.
4. Therefore a new Planner item can potentially persist those fabricated visual fallback coordinates as Canonical facts.

This violates the frozen rule:

> unknown business facts must remain unknown; UI fallback values must not become Canonical truth.

### Required fix

- represent visual fallback coordinates as explicitly non-canonical;
- never serialize fallback coordinates into Canonical Trip;
- add a regression:
  - source place coordinates = unknown;
  - Planner displays visual fallback;
  - user adds/reuses that place;
  - Canonical save must preserve coordinates as unknown/null, never fallback values.

Secondary hardening:

- where practical, authenticate before reading the bounded PUT body.

### Decision

**CHANGES REQUIRED before merge acceptance.**

After the fix, run TASK-069 focused + real Local HTTP/RLS/CAS tests against latest develop.
