# Trip Save / Read / History v1 — A/B handoff

- Contract: Trip Library persistence v1 (additive).
- Producer/owner: B, WBS 5.19 / TASK-049-B / Issue #333.
- Consumers: A Planner save integration (WBS 4.19, deferred); B Personal Center read client.
- Canonical content: existing A TripDraftFactsV1, WizardProgressV1 and TripPlanSnapshotV1.
- Migration: one additive B idempotency metadata column/index/guard; no A consumer migration.
- Examples/tests: TASK-049 contract fixtures, browser consumer build and real Cookie fetch acceptance.

## A entry point

Import only these public modules:

```ts
import type {
  TripPersistenceHandleV1,
  TripSavePlanRequestV1,
  TripSavePlanResultV1,
} from "@/shared/contracts/trip-library";
import { saveTripPlan } from "@/shared/contracts/trip-library/client";

// A obtains this opaque B handle from the authenticated Draft creation/read flow.
// A's canonical trip.id remains its existing stable string; never derive it from recordId.
const handle: TripPersistenceHandleV1 = existingHandle;
const request: TripSavePlanRequestV1 = { planSnapshot: canonicalSnapshot };
const result: TripSavePlanResultV1 = await saveTripPlan(handle, request);
// Retain result.storageRevision for the next save. Do not automatically retry a 409.
```

The helper uses same-origin Cookie fetch, no-store, exact If-Match, canonical A parsing,
and ETag validation. It returns only recordId, canonicalTripId, libraryState=saved,
storageRevision and updatedAt. It never imports B private persistence, server, DB,
Supabase, Planner runtime or credentials. Runtime source and consumer bundle tests prove
this boundary. Trip/Plan revisions inside the canonical snapshot are not storageRevision.
A's actual save button, handle lifecycle in Planner and cross-module UI E2E remain WBS 4.19/9.8.

## HTTP surface

All supported requests require verified Cookie or Bearer Auth. An explicit invalid Bearer
never falls back to Cookie. Cookie mutations require Origin equal to AUTH_SITE_URL's origin.
Every response generated by the gateway is private, no-store and varies on Authorization/Cookie.
Successful single-resource responses contain ETag: "<storageRevision>".

| Method | Path                           | Request                            | Success                 |
| ------ | ------------------------------ | ---------------------------------- | ----------------------- |
| POST   | /api/trip-library              | create below                       | 201 new / 200 retry     |
| GET    | /api/trip-library              | strict state, limit, cursor query  | 200 summary page        |
| GET    | /api/trip-library/{id}         | no query/body                      | 200 full owner resource |
| PUT    | /api/trip-library/{id}         | four-field Draft replacement below | 200                     |
| POST   | /api/trip-library/{id}/save    | schemaVersion=1.0, planSnapshot    | 200                     |
| POST   | /api/trip-library/{id}/history | empty body                         | 200                     |
| POST   | /api/trip-library/{id}/copy    | schemaVersion=1.0, creationKey     | 201 new / 200 retry     |
| DELETE | /api/trip-library/{id}         | empty body, Draft only             | 204                     |

Every mutation except create requires exactly a quoted positive int32 If-Match, for
example "7". Missing, weak, wildcard, multiple or malformed tags are 400; stale is 409.
History cannot be changed or deleted through v1. Saved cannot be updated through Draft PUT
or deleted. Save allows Draft→Saved and Saved→Saved; its canonical trip.id is immutable
once established. saved→history is explicit and uses the DB freeze clock.

### Create and Draft update

```ts
// POST /api/trip-library
{
  schemaVersion: "1.0",
  creationKey: crypto.randomUUID(),
  draftFacts,       // canonical TripDraftFactsV1
  wizardProgress,   // canonical WizardProgressV1
  preferenceOverridePatch, // optional at create, defaults to empty accepted PreferencePatchV1
  partySelection: {
    includesOwner: true,
    companionIds: [], // ordered unique owner UUIDs, max 100
    // ageReferenceDate: "2027-04-10" // required if no exact departure
  }
}

// PUT /api/trip-library/{id}: exactly four required fields, full replacement
{ draftFacts, wizardProgress, preferenceOverridePatch, partySelection }
```

PUT has no top-level schemaVersion or creationKey. The nested canonical payloads keep
those contracts' existing versions. The server captures the current long-term Preference
and selected Companions at create. A missing Preference is empty at revision 0. PUT retains
the original Preference snapshot while recapturing explicitly selected Companions.
The client cannot submit owner, B id, audit times, raw party/snapshot, source revision,
plan or canonicalTripId through these bodies. Current private roots are never written by
Trip requests. Effective Preference is snapshot + accepted trip-only patch.

Age reference prefers exact departure; otherwise an explicit strict local date is required.
Raw DOB is used only for deriving an age group and is never stored in party. The persisted
party is includesOwner, reference date and ordered trace UUID/name/planning age group/
accepted functional travel profile. No gender/avatar/relationship/private or medical notes.
Canonical participants are independent of the named Companion selection.

### Idempotency

For the lifetime of a record, creationKey is unique per verified owner. The first create
stores an immutable SHA-256 digest of its normalized request intent, independent of the
captured Preference/Companion values. Object key order, omitted empty create patch,
ignored fallback date when exact departure exists and order of keys in the unset list do not change
intent; Companion and canonical array order remains meaningful. Different create content,
create versus copy, or a different copy source conflicts with CREATION_KEY_CONFLICT.

A retry returns the existing record at its current state/revision, including after Draft
edits or History transition. It does not recapture roots or overwrite later changes.
Concurrent identical create/copy returns one 201 and one 200 with the same identity.
A copy retry still requires the source History's exact If-Match. Copy preserves source
Draft/progress/party, creates a new B UUID, captures the current Preference, clears the
patch, plan, canonical ID and freeze. It never invents an A ID. Pre-gateway 5.18 rows have
NULL intent metadata: they remain readable/mutable under v1, but cannot claim matching
create retry intent; reuse of their key conflicts. Physical Draft deletion releases its key;
clients should generate a fresh key for a new creation after an intentional deletion.

## B resources and list

B browser client: src/features/trip-library/persistence/client.ts. It exposes create/read/
update/save/history/copy/delete/list and validates responses through the B read model.
Success envelope is {ok:true,data}; failure is {ok:false,error:{code}}. A single resource
contains schemaVersion=1.0 plus the 5.18 record fields except ownerUserId, and derived
effectivePreference. Internal creationIntentHash is never in an API resource. It is not
an A-facing model. DELETE has no JSON response.

List query allows only state=all|draft|saved|history (default all), limit=1..50 (default20),
and opaque cursor. Duplicate/unknown parameters and malformed cursor versions fail.
Response is {schemaVersion:"1.0",items:TripLibrarySummaryV1[],nextCursor:string|null}.
The SQL projection contains only id, libraryState, canonicalTripId, storageRevision, title,
destination names, departure/returning, canonical participant total, wizard phase, plan
status and audit/freeze times. No full plan/draft/party/preferences or fabricated booking,
reservation, favorite or cover data. SQL fetches at most limit+1 summaries.

Order is updated_at DESC, id DESC. The opaque v1 cursor retains exact PostgreSQL microseconds
and the UUID tie-breaker, avoiding JavaScript Date precision loss. Traversing a stable dataset
has no duplicates/omissions. Pagination is not a cross-request snapshot: concurrent edits can
move rows ahead of a cursor; refresh from page one to see those changes. Do not interpret or
edit cursor contents or reuse a cursor with a different filter.

## Errors and technical bounds

| Code                                                                                                            | HTTP |
| --------------------------------------------------------------------------------------------------------------- | ---: |
| AUTH_REQUIRED                                                                                                   |  401 |
| AUTH_UNAVAILABLE                                                                                                |  503 |
| FORBIDDEN                                                                                                       |  403 |
| INVALID_REQUEST / INVALID_TRIP_DRAFT_INPUT / INVALID_TRIP_PLAN_INPUT / INVALID_TRIP_PREFERENCE_PATCH            |  400 |
| PAYLOAD_TOO_LARGE                                                                                               |  413 |
| TRIP_LIBRARY_NOT_FOUND                                                                                          |  404 |
| STALE_TRIP_LIBRARY_REVISION / TRIP_LIBRARY_STATE_CONFLICT / CREATION_KEY_CONFLICT / COMPANION_SELECTION_INVALID |  409 |
| TRIP_LIBRARY_UNAVAILABLE                                                                                        |  500 |

Cross-owner and nonexistent UUIDs both return 404. Errors never echo SQL, owner IDs or inputs.
For stale revision, read current state and resolve deliberately; no automatic last-write-wins.
For selection conflict, refresh authorized Companions. Unknown future codes need a generic
failure UI, not silent success. No service-role key is used in normal requests: verified Auth
precedes server-only getDb; each SQL query explicitly constrains owner_user_id and mutations
also constrain id, expected revision and allowed state. Direct authenticated DML stays denied.

Raw HTTP caps: create/update512KiB, save4.5MiB, copy16KiB, history/delete empty.
Existing Preference/Companion reader default stays80KiB; only Trip requests opt in.
5.18 JSONB text caps stay: draft256KiB, progress4KiB, plan4MiB, party128KiB,
Preference snapshot/patch64KiB. These are technical safety bounds, not subscription tiers.
Actual accepted stress plan: 4,194,304 JSONB bytes / 3,782,809 HTTP bytes; one additional
storage byte or excess HTTP body fails without partial write.

## Deferred visible integration

Trip Library's current fixture ViewModels require reservation completion/counts, favorites,
artwork and timing presentation that this contract does not persist. Follow-up must first
choose an honest Trip-only UI projection, unknown/absent handling and a product-approved
layout, then wire this client; it must not populate these fields with fake zeros or mock data.
Planner/Start/Personal Center/CSS are unchanged. No Reservation/Booking/Payment/Favorites
persistence, auto-archive, Start autosave, account deletion or downstream task is started.
