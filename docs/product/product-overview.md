# TravelAssist 产品总体设计书

> 状态：v0.1 / 产品设计冻结中  
> 更新日期：2026-09-04  
> 适用范围：Web 第一阶段 + 后续 App 扩展

## 1. 产品定位

TravelAssist 是一个以 **AI 对话 + 地图 + 行程时间轴 + 结构化偏好设置** 为核心的旅行规划工具。

目标不是只给用户一份静态攻略，而是把用户模糊的旅行需求转化为多套可比较、可解释、可继续调整的实际行程方案。

### 核心价值

1. 用户可以直接用自然语言描述旅行需求。
2. AI 将自然语言转换为结构化旅行条件与偏好。
3. 系统生成多个候选方案，而不是只给一个答案。
4. 用户在地图、时间轴和详细设置之间持续调整方案。
5. 交通、住宿区域、餐饮区域、景点与活动统一纳入同一套行程逻辑。
6. 用户不需要理解复杂参数，也可以通过“快速设置”完成大部分配置。
7. 对需要精细控制的用户，继续展开中项目和小项目进行设置。

## 2. 开发阶段

### Phase 1：Web

当前优先开发 Web 版本，用于：

- 快速验证产品结构与核心交互。
- 完成 AI 行程生成流程。
- 完成地图、时间轴、推荐方案和详细设置面板。
- 建立稳定的数据结构与 API。
- 通过桌面大屏验证复杂行程编辑体验。

### Phase 2：App

Web 核心功能稳定后再开发手机 App。

App 不应重新设计业务规则，而应尽量复用：

- 用户账号与旅行资料。
- 偏好模型。
- 行程数据结构。
- AI 行程生成与调整逻辑。
- 景点、交通、住宿、餐饮等数据接口。

移动端重点重新设计显示层和交互层。

## 3. 核心用户流程

```text
进入首页
  ↓
“让我们开始吧” / 登录
  ↓
AI 获取初始旅行需求
  ↓
必要时补充同行人、日期、目的地与偏好
  ↓
生成推荐方案 1 / 2 / 3 ...
  ↓
进入行程主页面
  ↓
地图 + 时间轴 + 右侧详细设置 + AI 对话
  ↓
用户选择方案或继续修改
  ↓
AI / 系统重新计算相关行程
  ↓
保存旅行方案
```

## 4. 核心系统构成

### 4.1 首页 / 入口

首页保持极简，不堆放大量宣传语。

主要元素：

- 主入口：`让我们开始吧`
- 登录入口
- 右下角 AI 按钮
- 点击 AI 按钮可以直接开始对话

视觉方向：

- 极简
- 圆润
- 轻量日本元素
- 顶部选单栏尽量小
- 可参考 Komoot 的沉浸式体验
- 背景可考虑使用动画 / 动态旅行画面
- 当前明确避免以绿色作为主视觉方案

详细页面规则见 `docs/ui/home-page.md`。

### 4.2 AI 对话系统

AI 是全局入口之一，不局限于单独聊天页面。

主要职责：

- 理解用户自然语言旅行需求。
- 提取日期、目的地、同行人、交通、景点等条件。
- 将模糊描述转换为系统偏好。
- 生成多个候选行程方案。
- 解释推荐理由。
- 根据用户后续自然语言重新调整局部或整体行程。

AI 与结构化设置必须保持同步：

```text
用户自然语言
     ↕
AI 解释层
     ↕
结构化旅行条件 / 偏好
     ↕
行程生成器
```

### 4.3 行程主页面

桌面版核心页面采用约 **左 3 / 右 1** 的结构。

左侧以地图为主，右侧设置面板以“镶嵌在地图内”的视觉方式呈现，避免传统后台式页面割裂感。

地图中展示：

- 每日路线
- 第一天 / 第二天 / 第三天等路线区分
- 推荐景点图钉
- 景点象征图片
- 步行、电车、公交等移动方式
- 推荐住宿区域
- 推荐午餐 / 晚餐区域

页面底部展示连续时间轴：

- 时间
- 景点 / 活动
- 交通方式
- 移动时间
- 午餐 / 晚餐
- 住宿等

右侧区域：

- 上方：详细设置
- 下方：推荐方案列表
- 推荐 1 显示相对详细的简略行程
- 推荐 2、3 等只显示方案名称 / 简要信息，向下延伸至屏幕底部

详细规则见 `docs/ui/trip-planner.md`。

### 4.4 偏好系统

偏好系统采用三级结构：

```text
大项目
  └─ 中项目（支持快速设置）
      └─ 小项目（高级详细设置）
```

设计原则：

- 默认界面只显示少量关键状态，降低第一次使用的复杂度。
- 中项目展开后提供快速设置。
- 用户需要更精细控制时，再展开小项目。
- 快速设置与详细设置共享同一份底层数据，不能形成两套互相冲突的参数。

同行人信息应优先于一般兴趣偏好设置，因为系统需要先理解旅行群体构成，再判断行程倾向。

当前已讨论的同行人类型包括：

- 成人男性
- 成人女性
- 小孩
- 婴儿

系统可据此辅助判断：亲子、情侣、朋友、家庭等旅行场景，但场景判断应作为推荐依据，不应未经用户确认强制改变所有偏好。

当前已明确的交通详细偏好示例：

- 少换乘
- 少步行
- 不乘坐公共交通
- 不乘坐公交
- 不乘坐游船

景点与活动设置应与快速设置联动，并支持比普通“景点类别”更细的旅行需求，例如拍照等行为偏好。

完整偏好分类见 `docs/preferences/preference-system.md`。

## 5. 多方案推荐

系统默认不只生成一条路线。

建议至少生成多套具有差异化的方案，例如：

- 推荐 1：综合平衡
- 推荐 2：更轻松 / 少移动
- 推荐 3：景点优先 / 内容更丰富

具体方案标签未来可以根据用户偏好动态生成，不需要固定成上述名称。

### 推荐方案应回答

- 为什么推荐该方案？
- 与其他方案相比差异在哪里？
- 主要交通强度如何？
- 每日节奏如何？
- 住宿区域为什么选这里？
- 哪些需求得到满足，哪些进行了取舍？

## 6. 地图与行程信息关系

地图不是单独的“查看地点”功能，而是旅行方案的主要可视化载体。

同一份行程数据应驱动：

```text
行程数据
 ├─ 地图路线
 ├─ 景点图钉
 ├─ 时间轴
 ├─ 交通段
 ├─ 住宿区域
 ├─ 餐饮区域
 ├─ 推荐方案摘要
 └─ AI 对行程的解释
```

任何一个入口修改行程后，都应尽量同步更新其他显示区域。

## 7. 信息层级

详细设置采用分层展示，避免一次暴露全部参数。

### 第一层：快速状态

默认只展示：

- 日期等关键旅行条件
- 少量当前生效的核心偏好
- 展开按钮

### 第二层：中项目

展开后显示各类主要设置，并允许快速调整。

例如：

- 同行人
- 移动偏好
- 景点与活动喜好
- 其他主要旅行条件

### 第三层：小项目

进一步展开时进入具体限制和高级偏好。

例如移动偏好可继续展开：

```text
移动偏好
├─ 少换乘
├─ 少步行
├─ 不乘坐公共交通
├─ 不乘坐公交
└─ 不乘坐游船
```

## 8. 设计原则

### 8.1 AI 优先，但不能只有 AI

用户可以自然语言操作，但关键旅行条件必须能够结构化查看和修改。

### 8.2 地图优先

复杂旅行路线应尽量直接在地图上理解，而不是只依赖文字列表。

### 8.3 渐进式复杂度

默认简单，必要时逐层展开。

### 8.4 所见即所得

修改交通、同行人、景点喜好等设置后，地图和时间轴应能反映变化。

### 8.5 推荐必须可解释

不只显示“推荐结果”，还应逐步实现“为什么这样推荐”。

### 8.6 设计与实现分离

产品规则先在 `docs/` 冻结，再交给 Codex 实现。Codex 不应自行补充未确认的业务规则。

## 9. 两人开发方式

项目采用 A / B 两人协作：

- A：约 70%，负责核心架构、关键模块、集成和发布。
- B：约 30%，负责可独立拆分模块、组件、测试、数据整理和临时接手任务。

工作以 GitHub Issue 为唯一开发任务入口。

分支约定：

```text
main
└─ 稳定 / 发布版本

develop
└─ 日常集成

feature/a-*
└─ A 功能

feature/b-*
└─ B 功能

fix/*
└─ Bug 修复
```

如果 A 某项任务因能力或时间无法完成，应把任务拆到独立 Issue，并由 B 从 `develop` 接手，不依赖某个人本机尚未提交的代码。

## 11. 尚未确定事项

以下内容仍属于待决策项，Codex 不应自行决定：

### 产品 / 商业

- 登录前能够使用到什么程度。
- 免费 / 付费功能边界。
- 是否允许公开分享行程。
- 是否加入社区 / UGC。

### 技术

- 最终 Web 前端技术栈。
- 地图库和地图数据供应商。
- 路线规划 / 公共交通数据供应商。
- 酒店、景点、餐饮数据源。
- AI 模型调用架构与成本控制方式。
- 后端、数据库和部署平台。

### UI / UX

- 最终主色、辅色与 Design Token。
- 首页动态背景最终形式。
- 日本元素具体表现方式与使用强度。
- 行程方案在手机端的最终交互结构。
- 地图推荐区域的最终图形表现规则。

### 推荐系统

- 多方案的固定数量还是动态数量。
- 方案评分公式。
- 各类偏好的权重算法。
- 同行人推断旅行类型的具体规则。
- 餐饮、住宿、景点推荐的最终排序算法。
