# TravelAssist 项目决策与设计总档

> 状态：项目主档 / 2026-09-04 快照  
> 用途：把当前项目讨论中已经形成的产品、UI/UX、AI、偏好、开发与协作设计集中保存到 GitHub。  
> 原则：详细规格以对应专题文档为准；本文件负责总览、状态与追踪。

## 1. 状态定义

- **已冻结**：可以作为 Codex / 开发直接实现依据。
- **方向已定**：总体方向已确定，但具体 token、枚举、技术方式或数值仍需冻结。
- **候选**：讨论过并值得保留，但不能当作正式业务规则。
- **待确认**：需要后续产品决策，开发不得自行补全。

---

## 2. 产品总定位

### 已冻结

- TravelAssist 是 **AI 对话 + 地图 + 行程时间轴 + 结构化偏好** 一体化旅行规划产品。
- 核心目标不是输出静态攻略，而是把模糊需求转化为 **多套可比较、可解释、可继续修改的实际行程**。
- 用户既可以自然语言操作，也可以通过结构化设置精细调整。
- 地图、时间轴、推荐方案、AI 和设置面板必须基于同一份结构化 Trip / Preference State。
- 系统应尽量减少重复提问；已经获取且仍有效的信息不再次询问。

### 核心闭环

```text
进入首页
  ↓
开始规划 / AI 对话
  ↓
提取目的地、日期、同行人、限制与偏好
  ↓
只补问必要缺口
  ↓
生成多个差异化候选方案
  ↓
地图主工作区
  ↓
地图 + 时间轴 + 推荐方案 + 偏好 + AI 联动修改
  ↓
保存旅行
```

## 3. 产品阶段

### 已冻结

1. **先 Web，后手机 App**。
2. Web 阶段优先验证复杂地图行程工作台、AI 流程和数据结构。
3. App 尽量复用 Web 阶段形成的账号、Trip State、Preference State、AI 逻辑、后端和数据接口。
4. App 重点重新设计显示与交互，不重新发明业务规则。

### 待确认

- App 是否采用跨平台框架还是原生方案。
- Web 与 App 的具体技术栈。

## 5. 首页设计

### 已冻结

- 首页不是传统营销落地页，目标是尽快开始旅行规划。
- 主 CTA：**“让我们开始吧”**。
- 有登录入口，但视觉优先级低于主 CTA。
- 右下角固定 AI 按钮；点击即可展开对话。
- 顶部导航尽量小，只保留必要入口。
- 页面总体：极简、圆润、沉浸式、少宣传语。
- UI 控件使用浮层 / 镶嵌感，不采用传统网页大量区块堆叠。
- 可吸收 Komoot 的沉浸式旅行 / 地图产品感，但不直接复制。
- 主视觉方案 **不使用绿色作为主色**。
- 加入轻量日本元素，但不做夸张日式装饰。

### 方向已定

- 动态旅行背景 / 动画背景是优先视觉方向。
- 首页 AI 打开后应仍能看到背景上下文，不切换成完全独立聊天页。
- 桌面端允许大面积背景；移动端优先保证主要操作。

### 待确认

- 最终主色与辅助色。
- 动画采用视频、Lottie、WebGL 还是 CSS。
- 日本元素具体表现：地形、季节、建筑、图案等。
- 登录入口最终位置。
- 点击“让我们开始吧”后直接进入 AI，还是先显示极简关键问题。
- 匿名用户可使用到什么程度。

## 6. 行程主工作区

### 已冻结：整体布局

- PC / Web 优先按 **16:9 宽屏**设计。
- 地图是绝对视觉主体。
- 整体视觉约 **左 3 / 右 1**。
- 右侧不是传统独立侧栏，而是“浮在 / 镶嵌在地图里”的卡片区域。
- 右侧上部：旅行条件与详细设置。
- 右侧下部：多方案推荐列表。
- 底部：连续行程时间轴，同样作为地图上的嵌入式信息层。

### 已冻结：地图表达

地图需要表达完整行程，不只是 POI 图钉：

- Day 1 / Day 2 / Day 3 等每日路线。
- 起点、终点与行程节点。
- 景点 / 活动图钉。
- 景点标记可以包含象征性缩略图片。
- 步行、电车 / 火车、公交等交通方式。
- 推荐住宿区域。
- 推荐午餐区域、晚餐区域。
- 已加入行程与仅推荐候选应可视觉区分。

### 设计原则

- 住宿和餐饮第一层先推荐 **区域**，避免地图被酒店 / 餐厅图钉淹没。
- 用户需要时再进入具体酒店或餐厅候选。
- 示例设计可使用“3 天 2 晚”来验证信息密度，但这不是产品固定天数。

### 底部时间轴

时间轴可包含：

- 时间
- 景点 / 活动
- 交通方式
- 移动时间
- 午餐 / 晚餐
- Check-in / 住宿

长期方向：时间轴逐步从展示升级为编辑入口；拖拽、调整停留、删除、替换等具体功能尚未全部冻结。

设计图：`assets/design/trip-planner-concept.svg`。

## 7. 右上详细设置 / 信息层级

### 已冻结

默认状态不展示完整复杂表单，只显示：

- 日期 / 行程长度
- 同行人概要
- 当前旅行节奏
- 交通关键偏好
- 景点喜好概要
- 展开 / 详细设置入口

设置采用三层：

```text
第一层：关键摘要
   ↓ 展开
第二层：中项目 + 快速设置
   ↓ 展开某一中项目
第三层：小项目 / 详细限制
```

### 中项目方向

- 同行人
- 日期与行程条件
- 移动 / 交通
- 景点与活动
- 餐饮
- 住宿
- 行程节奏
- 其他限制

设计图：`assets/design/preference-panel-concept.svg`。

## 8. 同行人设计

### 已冻结

同行人应放在普通兴趣偏好之前，因为它会影响整个推荐逻辑。

当前至少考虑数量：

- 成人男性
- 成人女性
- 小孩
- 婴儿

系统可根据组合辅助推断：

- 亲子
- 情侣
- 家庭
- 朋友

但推断只作为推荐输入，不覆盖用户明确设置。

### 可能受同行人影响

- 步行强度
- 换乘次数
- 休息频率
- 儿童 / 婴儿友好性
- 用餐时段
- 夜间活动
- 住宿区域

### 待确认

- 小孩年龄是否进一步分级。
- 同行人性别是否需要长期保存。

## 9. 偏好系统

### 已冻结：三级结构

```text
大项目
  └─ 中项目：主要设置层 / 快速设置
       └─ 小项目：高级详细设置
```

原则：**默认简单，按需深入，AI 与表单共享同一份参数。**

### 移动 / 交通

已讨论并可作为当前设计依据：

- 轻松优先 / 平衡 / 效率优先（快速方向，具体枚举仍可复核）
- 少换乘
- 少步行
- 不乘坐公共交通
- 不乘坐公交
- 不乘坐游船

冲突时，例如“少步行 + 不乘公共交通”，系统不得静默忽略；应提示冲突、解释取舍，必要时询问优先级。

### 景点与活动

- 不能只设计传统景点类别。
- 需要支持用户“为什么去”的行为目的，例如 **拍照**。
- 快速层尽量只显示喜好，而不是复杂评分表。
- 必去 / 希望去 / 可去 / 不去、热门 / 小众、室内 / 室外等属于后续可扩充方向，尚未全部冻结。

### 餐饮

- 餐饮参与路线与时间安排，不是独立餐厅搜索功能。
- 第一层优先显示午餐 / 晚餐区域。
- 菜系、预算、排队、儿童友好、饮食限制等详细枚举待确认。

### 住宿

- 先解决住宿区域是否合理，再进入具体酒店。
- 住宿选择需要考虑每日交通、换酒店次数、夜间活动和次日出发效率。
- 星级、预算、房型等枚举待确认。

## 10. 多方案推荐

### 已冻结

- 系统不应只生成一个答案，应生成多个 **真正有差异** 的候选方案。
- 推荐 1 是当前主推荐，右侧显示更完整摘要。
- 推荐 2、3 等默认只显示名称、差异说明和少量关键指标。
- 用户选择其他方案后，该方案转为当前主方案并展开。

每个方案逐步需要解释：

- 核心特点
- 每日概要
- 交通强度
- 旅行节奏
- 推荐住宿区域理由
- 满足了哪些偏好
- 做了哪些取舍

“综合平衡 / 更轻松 / 景点优先”等是候选标签示例，不固定为永久名称。

## 11. AI 设计

### 已冻结

AI 不是独立聊天机器人，而是 TravelAssist 的自然语言交互层：

```text
User Message
   ↓
意图 / 条件提取
   ↓
Trip / Preference Patch
   ↓
冲突验证
   ↓
Planner / Recommender
   ↓
Trip State
   ├─ Map
   ├─ Timeline
   ├─ Recommendation Cards
   └─ AI Explanation
```

AI 负责：

- 理解自然语言旅行需求。
- 提取目的地、日期、同行人、硬限制与偏好。
- 只补问必要缺口。
- 生成多个方案。
- 根据后续语言修改局部或整体行程。
- 将修改同步到结构化状态。
- 解释变化和取舍。

### AI 禁止事项

- 不把聊天文本作为唯一事实源。
- 不重复询问已保存且仍有效的信息。
- 不静默违反硬限制。
- 不事后编造与实际规划结果无关的推荐理由。
- 不把“待确认”产品规则擅自实现为永久规则。

设计图：`assets/design/ai-trip-flow.svg`。

## 12. 数据 / 状态设计原则

### 已冻结

同一旅行只有一个业务事实源。

```text
Trip State
 ├─ Map View
 ├─ Timeline View
 ├─ Recommendation View
 ├─ Settings Panel
 └─ AI Context
```

Preference 至少需要区分：

- 用户长期偏好
- 本次旅行偏好
- 硬限制
- 软偏好

### 待冻结技术规格

- Trip / Day / Segment / Place / Transport / Meal / Stay Schema
- Preference State Schema
- UI 临时状态与持久化业务状态边界
- Schema 版本与迁移
- API 边界

对应 GitHub Issue 已建立，技术文档放在 `docs/architecture/`。

## 14. 开发与协作决策

### 已冻结

- GitHub 是正式工程与设计记录入口。
- `main`：稳定 / 发布。
- `develop`：日常集成。
- 功能：`feature/*`。
- Bug：`fix/*`。
- 正式开发任务必须 Issue 化。
- 功能通过 PR 合回 `develop`，稳定节点再进 `main`。
- A 约 70%，B 约 30%。
- A 主核心架构、状态、AI、地图核心、集成和发布。
- B 主独立 UI / 组件、设置、测试、数据、文档和可拆分接手任务。
- A 赶不上时，优先把边界清楚的完整 Issue 转交 B。
- 交接建立在已 Push 的代码、明确接口、Issue Checklist 和验收条件上。
- Codex / GPT 开发前必须阅读 `README.md`、`CONTRIBUTING.md`、对应 `docs/` 与 Issue。
