# 已确认设计决策

> 本文件只记录已经可以作为开发依据的决策。讨论稿、候选方案和未确认想法不写入“已确认”。完整上下文见 `project-design-master.md`。

## 2026-09-04

### 产品阶段

- [已确认] 先开发 Web 版本，再扩展手机 App。
- [已确认] App 尽量复用 Web 阶段形成的数据结构、业务逻辑与后端能力。

### 产品总体

- [已确认] 核心体验由 AI 对话、地图、行程时间轴、结构化偏好共同组成。
- [已确认] 系统生成多个差异化候选方案，而不是只给一份静态攻略。
- [已确认] AI、地图、时间轴、推荐方案和设置面板共享同一份结构化 Trip / Preference State。

### 首页

- [已确认] 首页保持极简，不堆放大量宣传语。
- [已确认] 首页主入口为“让我们开始吧”。
- [已确认] 首页包含登录入口。
- [已确认] 右下角提供 AI 入口，可直接开始对话。
- [已确认] 顶部选单 / 导航保持小型化，只保留必要入口。
- [已确认] 整体视觉偏圆润、沉浸式。
- [已确认] 可吸收 Komoot 的地图产品感与沉浸式体验，但不直接复制。
- [已确认] 动态旅行画面 / 动画背景作为首页正式视觉方向；具体实现技术仍待确认。
- [已确认] 当前主视觉方案不使用绿色作为主色。
- [已确认] 可以加入适量日本元素，但最终表现方式仍待设计。
- [已确认] AI 打开时尽量使用浮层 / 镶嵌形式，不把首页直接切换成传统独立聊天页。

### 行程主页面

- [已确认] 桌面版核心页面以地图为主体。
- [已确认] PC 核心画布优先按 16:9 宽屏设计与验收。
- [已确认] 页面整体约为左 3 / 右 1 的视觉比例。
- [已确认] 右侧设置区域采用镶嵌 / 浮在地图内的表现方式。
- [已确认] 右侧上部为关键条件摘要与详细设置区域。
- [已确认] 默认状态只展示日期、同行人、节奏、移动与景点喜好等少量关键内容，并提供展开入口。
- [已确认] 右侧下部为推荐方案列表。
- [已确认] 推荐 1 显示更完整摘要；推荐 2、3 等默认只显示名称、极短差异信息或少量关键指标，选中后再展开。
- [已确认] 页面底部设置连续行程时间轴。
- [已确认] 时间轴同时包含时间、景点 / 活动、交通、餐饮、住宿等行程信息。
- [已确认] 地图中需要表达步行、电车 / 火车、公交等交通方式。
- [已确认] 地图可以展示推荐住宿区域。
- [已确认] 地图可以展示推荐午餐 / 晚餐区域。
- [已确认] 景点使用地图标记，并可使用象征图片增强辨识度。
- [已确认] 住宿与餐饮第一层优先推荐区域，再按需展开具体酒店 / 餐厅候选。
- [已确认] “3 天 2 晚”用于当前 Mock / 设计验证，不是产品固定旅行长度。

### 偏好系统

- [已确认] 偏好采用“大项目 → 中项目 → 小项目”三级结构。
- [已确认] 默认只展示少量关键内容，不一次展开全部详细设置。
- [已确认] 中项目提供快速设置。
- [已确认] 小项目用于高级详细设置。
- [已确认] 同行人设置应放在较前位置。
- [已确认] 当前同行人至少包含成人男性、成人女性、小孩、婴儿数量。
- [已确认] 系统可利用同行人组合辅助判断亲子、情侣、家庭、朋友等旅行倾向，但不能覆盖用户明确偏好。
- [已确认] 移动偏好包含少换乘、少步行等方向。
- [已确认] 已讨论的小项包含不乘坐公共交通、不乘坐公交、不乘坐游船。
- [已确认] 景点与活动偏好不能只停留在大类，需要支持拍照等更细行为偏好。
- [已确认] 景点与活动的快速层优先显示“喜好摘要”，复杂类别、行为和限制下沉到详细层。
- [已确认] 偏好冲突不能被静默忽略；系统需要提示、解释取舍，并在必要时询问优先级。

### 多方案推荐

- [已确认] 候选方案之间需要有实际差异，不应只是相同路线小幅换序。
- [已确认] 当前主推荐展示更多信息，其他方案保持精简以控制右侧信息密度。
- [已确认] 推荐结果逐步支持解释“为什么这样安排”和“做了什么取舍”。

### AI

- [已确认] AI 是全局交互入口，不是孤立聊天页。
- [已确认] AI 能把自然语言转换为结构化旅行条件和偏好。
- [已确认] AI 生成多个候选行程方案。
- [已确认] AI 可以根据后续自然语言修改行程。
- [已确认] AI、地图、时间轴、设置面板需要共享同一份结构化 Trip / Preference State。
- [已确认] 已经获取且仍有效的信息不应重复询问。
- [已确认] AI 不得把聊天文本作为唯一业务事实源。
- [已确认] 用户明确硬限制与系统默认冲突时，不得静默忽略用户限制。

### 视觉与设计资产

- [已确认] UI 整体避免传统 OTA 搜索列表和企业后台感。
- [已确认] 视觉控件采用圆润、浮层、镶嵌式关系。
- [已确认] 设计图和正式视觉资产统一进入 GitHub `assets/design/` 版本管理。
- [已确认] 当前 canonical 概念图包括：首页、行程主工作区、三级偏好面板、AI Trip 数据流。

### 开发协作

- [已确认] GitHub 作为正式开发与协作入口。
- [已确认] `main` 保存稳定 / 发布版本。
- [已确认] `develop` 用作日常集成分支。
- [已确认] 功能开发使用 `feature/*`，Bug 使用 `fix/*`。
- [已确认] A 约承担 70%，B 约承担 30%。
- [已确认] A 主要负责核心架构、关键功能、集成和发布。
- [已确认] B 主要负责可独立拆分的页面、组件、测试、数据整理与临时接手任务。
- [已确认] 正式工作使用 GitHub Issue 记录，而不是只依赖聊天内容。
- [已确认] A 时间或能力不足时，可将边界清楚的任务完整转交 B；交接以已 Push 代码、Issue 和验收条件为基础。
- [已确认] Codex 实现前必须阅读对应设计文档、设计图（UI 任务）与 Issue，不自行补充未确认业务规则。
